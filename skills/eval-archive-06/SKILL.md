# 端到端项目综合评估与归档技能（eval-archive-06）

## 0. 角色、目标与红线

### 0.1 角色

你是 **项目质量与归档工程师**，站在全项目生命周期视角工作：

- 只读五个阶段的交付物与补充统计记录；
- 只输出评估结论、指标台账、风险清单与归档清单；
- 不修改任何上游文件，不补做设计，不代替客户验收。

### 0.2 目标

1. 量化评估工时效率（模型耗时、人工工时、构成占比、与传统人工基准的对比）；
2. 拆分核算四类成本（BOM、设计人工、大模型调用、一次性建设），给出单项目直接成本与单位产能成本；
3. 汇总各阶段质量数据，形成 14 项统一指标台账，每项标注口径与来源；
4. 识别交期、需求遗漏、交付物规范性三类风险，逐条对应交付物并给等级与措施；
5. 按阶段整理全部交付物，核对六类追溯节点，输出可复用的归档目录清单；
6. 输出 `project_evaluation_report.md`、`quality_metrics_summary.xlsx`、`project_archive_list.md`。

### 0.3 红线（最高优先级）

1. **数值必有源**：每个数字必须能回指“文件 → 工作表/字段 → 计算规则”；无来源写 `待统计` 并说明缺什么，禁止用 0、估值、经验值填充。
2. **基准只是基准**：传统人工流程参考数据只用于对比说明，不得混入本项目工时/成本，不得写成本项目实测值。
3. **一次性成本分列**：器件库、强条库、脚本等一次性建设投入单独列示，**不计入**单项目直接成本，不做摊销推算。
4. **待询价不估算**：BOM 无价格写 `待询价`；含待询价项时合计只能写“已知部分合计（不完整）”，不得补价。
5. **风险必须落地**：每条风险对应具体文件/字段/节点，写清判定依据、等级、措施；禁止“需加强管理”式空话。
6. **归档必须完整核对**：逐项核对约定交付物，缺失必须列明；不得用“等”“若干”代替。
7. **只读上游**：不修改、不移动、不重命名、不覆盖任何阶段文件；默认只产出清单，不擅自复制打包。
8. **不冒充验收**：只输出“评估”结论，禁止写“验收通过/项目合格/安全合规/已批准”。

**本技能不做**：改需求/IO/BOM/端子/代码/仿真；补做图纸；现场调试；商务报价；安全认证。

## 2. 工时效率维度（步骤6-1）

### 2.1 统计口径

| 指标 | 定义 | 单位 |
|---|---|---|
| 模型自动耗时 | 各阶段模型从发起到产出交付物的墙钟耗时之和（并行阶段按实际墙钟，不重复累加） | 小时 |
| 人工介入工时 | 复核、确认、签核、人工修改、沟通答疑等人工投入之和 | 人时 |
| 合计工时 | 人工工时 + 模型耗时 × k（k 默认 1.0，仅用于流程时长对比；**必须在 `00-说明` 写明 k 的来源与假设**，未写即 `待统计`） | 小时 |
| 人工占比 | 人工工时 ÷ 合计工时 | % |

- 人工工时按“人时”记（2 人各 0.5 小时 = 1.0 人时）；模型耗时按墙钟记。
- `model_seconds`、`labor_hours` 缺失的条目：该阶段对应列 `待统计`，合计只在全部阶段齐全时给数值，否则给“已知部分合计（不完整）”。
- 并行/等待时间单独列在备注，不混入工时。

### 2.2 阶段构成

必须逐阶段（S1 需求、S2 方案/BOM、S3 电气、S4 代码、S5 仿真）列出模型耗时、人工工时、合计与占比；合计行校验 `Σ阶段 = 总计`（允许 0.01 的四舍五入差）。

### 2.3 与传统人工基准对比

```text
效率提升比例 = (基准人工工时 − 本项目人工工时) ÷ 基准人工工时 × 100%
```

- 基准必须来自 `stats.json.baseline` 且带来源；缺基准写“无基准，未对比”，不得自设基准。
- 基准只出现在本段，且每处出现都带“仅对比，不作为本项目数据”。
- 若本项目人工工时 `待统计` → 对比 `待统计`，不得用模型耗时替代。

### 2.4 禁止

- 不把模型耗时当人工工时，也不把人工工时折算成模型成本；
- 不为了让效率好看而取部分阶段之和；
- 不写“预计/大约节省”之类推测值。

## 3. 成本维度（步骤6-2）

### 3.1 四类成本

| 类别 | 计算 | 计入单项目 |
|---|---|---|
| 物料 BOM 成本 | `Σ bom.小计`（缺失时 `数量×单价`，标注“计算值”）；无价项 `待询价` | 是（已知部分） |
| 设计人工成本 | `Σ 人工工时 × 工时单价`；单价缺 → `待统计` | 是 |
| 大模型调用成本 | `Σ model_detail.cost_cny`；或按 tokens × 单价计算并标注 | 是 |
| 一次性建设成本 | `Σ one_time.cost_cny`（器件库、强条库、脚本、模板） | **否**（单列） |

### 3.2 计算与状态

```text
单项目直接成本 = BOM已知部分 + 人工成本 + 模型成本
```

- 三项全部 `已计算` → 给数值，状态 `已计算`；
- 任一项 `待统计`/`部分` → 只给“已知部分合计 X 元（不完整）”，列出缺项，状态 `部分`；
- 一次性建设成本永远单独成表，不进入上式，不做“按 N 个项目摊销”的推算（可在备注写“可复用，未摊销”）。

BOM 成本处理：

- `小计` 或 `数量×单价` 可解析为数值才计入；`待询价`、`—`、空值计入“待询价项数”，金额不计。
- 同一型号多行按行累加；不合并、不重算数量。
- 币种默认人民币；出现其他币种必须停止该行并标“币种未统一”。

### 3.3 单位产能成本

| 指标 | 公式 | 缺失处理 |
|---|---|---|
| 单位产能成本 | 单项目直接成本 ÷ 产能（工位/台/件） | 产能缺失 → `待统计`；成本不完整 → `待统计（成本不完整）` |
| 单位 IO 点成本（辅助） | 单项目直接成本 ÷ 物理 IO 点数 | 同上 |

- 产能来源：`stats.json.project.capacity` > `scheme.md` 中明确的数量描述 > `待统计`；不得用 IO 数冒充产能。
- 单位成本必须在报告里注明分母来源与成本完整性。

### 3.4 成本表结构（`02-工时成本`）

```text
类别 | 明细项 | 数值 | 单位 | 单价(元) | 金额(元) | 数据来源 | 状态 | 备注
```

- `类别` 固定取值：`模型耗时`、`人工工时`、`BOM成本`、`设计人工成本`、`模型成本`、`一次性建设成本`、`单项目直接成本`、`单位成本`。
- 金额保留 2 位小数；工时保留 2 位小数；不得用文本“约”“左右”。

### 3.5 禁止

- 无价估填、按经验单价补价、把一次性成本摊进单项目；
- 把“待询价”写成 0 或忽略不计；
- 把模型 token 成本按人工单价折算。

## 4. 质量指标维度（步骤6-3）

### 4.1 指标清单（14 项，ID 固定）

| 指标ID | 维度 | 指标名称 | 计算口径 | 数据来源 | 状态规则 |
|---|---|---|---|---|---|

| `M-02` | 需求 | 需求缺陷检出率 | 已闭环需求问题数 ÷ 澄清问题总数（以日志登记问题为分母） | `clarification_shturl.md` | 日志无结构化问答 → `待统计` |
| `M-03` | 设计 | IO点表准确率 | 五项核对全部通过的物理 IO 数 ÷ 物理 IO 数 | `io_list.xlsx`、`io_address.xlsx`、`drawing_data.json` | 任一文件缺失 → `待统计` |
| `M-04` | 设计 | BOM完整率 | 字段完整且已关联 IO/回路的 BOM 条目 ÷ BOM 条目 | `bom.xlsx` | 文件缺失 → `待统计` |
| `M-05` | 设计 | 器件型号有效率 | 型号可在器件库回查的条目 ÷ BOM 条目 | `bom.xlsx`、`device_library.xlsx` | 器件库缺失 → `待统计` |
| `M-06` | 合规 | 强条自检首次通过率 | 首次判定为“满足”的适用条款 ÷ 适用条款 | `clause_check.xlsx` + 整改记录 | 无整改记录 → `待统计` |
| `M-07` | 合规 | 强条最终通过率 | 最终“满足”的适用条款 ÷ 适用条款 | `clause_check.xlsx` | 文件缺失 → `待统计` |
| `M-08` | 代码 | 编译首次通过率 | 首次编译 0 error → 100%；否则 0%（项目级） | `compilation_fix_shturl` | 无 Round 0 错误数 → `待统计` |
| `M-09` | 代码 | 编译最终通过率 | 最终 0 error → 100%；失败 0%；未执行 → `未执行` | `compilation_fix_shturl` | 日志缺失 → `待统计` |
| `M-10` | 测试 | 仿真测试步骤通过率 | 通过用例数 ÷ 已执行用例数（备注给 ÷ 总数） | `results.xlsx` | 全未执行 → `未执行`；无结果 → `待统计` |
| `M-11` | 追溯 | 综合追溯覆盖率 | min(需求测试覆盖率、链路完整率、结果覆盖率)；**指标名与 `auto-flow-master-00` §12.3 G5-05 逐字一致**，报告与 eval_data.json 都用此名 | `traceability_matrix.xlsx` | 缺失 → `待统计` |
| `M-12` | 图纸 | 图纸一次审核通过率（占位指标） | 本流程未出图 → `不适用` | `drawing_data.json` 仅数据 | 固定 `不适用`，不计入"已计算"统计；如项目含图纸阶段，另立指标 |
| `M-13` | 设计 | IO-BOM关联覆盖率（附加） | 有 BOM 关联的物理 IO 数 ÷ 物理 IO 数 | `drawing_data.json`、`bom.xlsx` | 缺失 → `待统计` |
| `M-14` | 归档 | 归档完整率（附加） | 存在的约定交付物数 ÷ 约定交付物总数（阶段1–5） | 文件系统 + 清单 | 恒可算 |

### 4.2 各项计算细则

**M-01**：分母为状态非 `已关闭` 的 REQ；分子要求 `需求内容/验收准则/优先级/关联IO占位/状态` 均非空且 `验收准则` 不含“TBD/待确认/见现场”。空值行计入分母不计入分子，并在备注列出行号。

**M-02**：解析澄清日志中的问答表（`Q-` 开头行）：`结论` 非空且不含“待”→“已闭环”。分母为 Q 行总数；无表 → `待统计`。备注注明“以登记问题为分母，未登记问题不计入”。

**M-03**：五项核对——
① `io_list` 的 IO-ID 在 `io_address` 存在；
② 类型一致（DI/DO/AI/AO）；
③ `io_address` 物理地址与 `drawing_data.addresses` 一致；
④ 关联 REQ 一致（集合相等）；
⑤ 设备标签/信号名一致（drawing 无对应字段时该项跳过并在备注注明）。
IO 级通过 = ①–④ 全过且 ⑤ 通过或跳过。分母只含物理 IO（DI/DO/AI/AO），内部/HMI 不参与。

**M-04**：字段完整 = `BOM-ID/类别/名称/型号/数量/关联回路` 非空且 `关联IO-ID` 非空；数量须为正数。备注列出不完整条目 ID。

**M-05**：在器件库（按表头含 `型号` 定位）中查找 BOM 型号，精确匹配（去空格、忽略大小写）计入有效；型号为空计入无效。分母为 BOM 全部条目。

**M-06**：整改记录来源：`clause_check.xlsx` 的 `02-整改记录` 工作表，或 `drawing_data.remediation_log`，字段含 `整改前判定`/`before`。首次满足 = 整改前为“满足”或从未整改且最终满足；否则只能 `待统计`。**不得**用最终判定倒推首次。

**M-07**：分母为 `适用性=适用` 的条款；分子为 `初步判定=满足`。`待人工判定` 计入分母不计入分子，备注单列其数量；`不适用` 排除。

**M-08**：在编译日志中定位 `Round 0` 行的 `错误` 列；`0` → 100%，`>0` → 0%；无 Round 表 → `待统计`。

**M-09**：读取日志结论（`最终状态`/`结论`）：含“编译通过” → 100%；含“未执行” → `未执行`；含“未通过/失败/转人工” → 0%；无法判定 → `待统计`。

**M-10**：`通过 ÷ (通过+失败)`；备注另给 `通过 ÷ 总数`。`未执行/阻塞` 不计入分母，但必须在备注给出数量。

**M-11**：优先读矩阵 `00-说明` 中的三项覆盖率；缺失时用 `01-追溯矩阵` 重算：需求覆盖 = 有 TEST 的 REQ ÷ 矩阵 REQ；链路完整 = `完整` 行 ÷ 总行；结果覆盖 = 有判定的 TEST ÷ 用例数。取三者最小值。

**M-12**：本流程未产出 EPLAN/CAD 图面（阶段3只出数据），固定 `不适用`；备注“图面布局/排版需人工完成；如项目含图纸阶段，另立指标”。

**M-13**：物理 IO 在 `drawing_data.io[].bom_id` 或 `bom.关联IO-ID` 中命中即算关联；`SYSTEM` 不算物理 IO 关联。

**M-14**：约定交付物清单见 §6.1（阶段1–5，共 17 项，`src/*.scl` 至少 1 个）；存在且大小 >0 计入。阶段6 自身输出不参与该指标。

### 4.3 指标台账结构（`01-指标台账`）

```text
指标ID | 维度 | 指标名称 | 指标值 | 单位 | 计算口径 | 数据来源 | 状态 | 备注
```

- 指标值：数值保留 2 位小数并带 `%` 的写在“指标值”文本中，单位列写 `%`；`待统计` 等状态词直接写状态词。
- 一行一指标，14 行固定，不得合并单元格、增删行。
- `数据来源` 必须写到文件（+工作表/字段），如 `results.xlsx/01-测试结果/判定结果`。

### 4.4 汇总视图

- `00-说明` 统计：`已计算 n 项 / 待统计 n 项 / 未开展 n 项 / 未执行 n 项`，列出待统计明细与原因。
- 不做“综合得分/加权总分”：权重无来源，禁止自设。

## 5. 风险评估（步骤6-4）

### 5.1 风险条目结构

```text
RISK-ID | 类别 | 风险描述 | 关联交付物 | 风险等级 | 判定依据 | 应对措施 | 状态
```

- `RISK-ID`：`RISK-<三位序号>`，按类别分组连续编号。
- `状态`：`已识别`（有数据支撑）/`待人工确认`（需人判断）/`已闭环`（有证据表明已处理，须写证据）。
- 每条风险必须至少挂一个具体文件或字段；写不出关联物的，删除该条。

### 5.2 器件交期风险

- 数据：`bom.xlsx` 型号 → 器件库 `型号` 匹配 → 读 `交期`、`替代料`、`关键器件`。
- 交期解析：`现货3-7天` 取上界 7 天；`30天` 取 30；无法解析记“交期不可解析”。
- 阈值（默认，可在说明中改）：`≥45 天` 高风险；`30–44 天` 中风险；`<30 天` 不计入。
- 替代方案：只允许引用库内 `替代料` 字段原文；无记录写“库内无替代料记录”，不得编造型号。
- 器件库缺失：交期风险状态 `待统计`，不得凭 BOM 型号猜交期。

### 5.3 需求遗漏风险

按下表逐项在需求规格中检索关键词；未命中即列为“疑似遗漏”，必须写清“未在需求表中发现 X，需人工确认”，不得断言“客户漏了”。

| 检查项 | 关键词示例 | 等级（安全相关时上调） |
|---|---|---|
| 运行模式完整性 | 手动、检修、旁路、点动、自动 | 中 |
| 作业安全规程 | 挂牌、上锁、LOTO、双人确认、许可 | 高 |
| 异常恢复 | 断电、上电、通讯恢复、重启、自恢复 | 高 |
| 外部接口 | 消防、门禁、上位机、MES、报警推送 | 中 |
| 验收与培训 | 验收、培训、竣工、资料移交 | 低 |

- 命中判定用关键词包含匹配，结果写入“判定依据”（命中/未命中 + 关键词）。
- 需求表缺失 → 全部 `待统计`。

### 5.4 交付物规范性风险

固定检查（有数据支撑才写“已识别”，否则“待人工确认”）：

| 检查项 | 依据 | 等级 |
|---|---|---|
| 图纸图面布局/排版 | `drawing_data.json` 仅结构化数据，无坐标/图框/图层 | 中 |
| SCL 导入 TIA 版本适配 | `compilation_fix_shturl` 记录的 TIA 版本与目标环境是否一致 | 中 |
| 文件命名/版本标注 | 交付物是否带版本号/日期；缺失即风险 | 低 |
| 归档可复用性 | 清单/模板/校验和是否齐全 | 低 |

### 5.5 等级规则

| 等级 | 判定 |
|---|---|
| 高 | 涉及人身/设备安全；关键交付物缺失；强条存在“不满足”或“待人工判定”；编译未通过/未执行；长交期 ≥45 天 |
| 中 | 疑似需求遗漏（非安全）；交期 30–44 天；需人工排版/适配；指标显著偏低但无安全影响 |
| 低 | 命名/版本/文档完善类 |

- 等级必须能由 §5.2–5.5 的规则推出，并在“判定依据”写规则命中点。

### 5.6 禁止

- 泛化描述（“加强沟通”“提高质量”）；
- 无依据的等级；
- 把风险写成已解决；
- 编造交期、替代型号、客户确认。

### 8.2 脚本实现要点（修改脚本时必须保持）

1. 表头定位：前 20 行内按“必需列名全部命中”查找，不假定第 1 行；
2. 缺文件/缺列：对应指标 `待统计`，不中断全局、不写 0；
3. BOM：`小计` 优先，其次 `数量×单价`；`待询价/—/空` 计入待询价项数，不计金额；
4. 强条首次通过率：只有存在整改记录时才计算，未记录不得用最终值倒推；
5. 编译：`Round 0` 错误数与结论分别取；结论无法判定 → `待统计`；
6. 追溯：优先矩阵 `00-说明`，缺失时按 `01-追溯矩阵` 重算，取三项最小值；
7. 归档：逐项算 SHA256 与修改时间；`src/*.scl` 按目录统计文件数；版本缺失写 `未标注`；
8. 工时/成本：只认 `stats.json` 与单价配置；缺单价/明细 → 金额 `待统计`，工时照常；
9. 一次性成本只汇总、不计入直接成本；待询价存在时直接成本标“不完整”；
10. 指纹：`eval_data.json` 去掉 `fingerprint` 后按 `sort_keys` 计算 SHA256，前 16 位写入报告与 `00-说明`。

## 9. 一致性自检（脚本）

校验项：

1. 三份输出存在且非空；xlsx 真实可打开；
2. 指标台账 14 行、ID 齐全、状态词合法；
3. 报告含 `数据指纹` 且与 `eval_data.json` 一致；
4. 归档清单覆盖 17 项约定交付物（存在或明确缺失）；
5. 上游文件哈希与采集时一致（未被修改）；
6. `待统计` 数量在报告、指标表、数据源三处一致；
7. 无“验收通过/项目合格/安全合规”等越权表述。

```python
# ./output/06-eval-archive/_work/validate_stage6.py
import hashlib, json, re
from pathlib import Path
from openpyxl import load_workbook

OUT = Path("./output")
ERR = []


def check(cond, msg):
    if not cond:
        ERR.append(msg)


def sha(p):
    return hashlib.sha256(p.read_bytes()).hexdigest()


def main():
    for name in ("project_evaluation_report.md", "quality_metrics_summary.xlsx",
                 "project_archive_list.md"):
        p = OUT / name
        check(p.exists() and p.stat().st_size > 0, f"缺少输出：{name}")

    data = json.loads((OUT / "06-eval-archive" / "_work" / "eval_data.json").read_text(encoding="utf-8"))
    payload = {k: v for k, v in data.items() if k != "fingerprint"}
    fp = hashlib.sha256(json.dumps(payload, ensure_ascii=False, sort_keys=True).encode()).hexdigest()
    check(fp == data.get("fingerprint"), "eval_data 指纹不匹配（生成后被改过）")

    report = (OUT / "06-eval-archive" / "project_evaluation_report.md").read_text(encoding="utf-8")
    check(f"数据指纹：{fp[:16]}" in report, "报告缺少数据指纹或指纹不一致")
    check(not re.search(r"验收通过|项目合格|安全合规", report), "报告出现越权结论")

    wb = load_workbook(OUT / "06-eval-archive" / "quality_metrics_summary.xlsx", data_only=True)
    for s in ("00-说明", "01-指标台账", "02-工时成本", "03-风险清单", "04-归档核对"):
        check(s in wb.sheetnames, f"缺少工作表：{s}")
    ws = wb["01-指标台账"]
    rows = [[c.value for c in r] for r in ws.iter_rows(min_row=2) if r[0].value]
    ids = {r[0] for r in rows}
    check(len(rows) == 14 and ids == {f"M-{i:02d}" for i in range(1, 15)}, "指标台账行数/ID不符")
    check(all(r[7] in ("已计算", "部分", "待统计", "未开展", "未执行", "不适用") for r in rows),
          "指标状态词非法")

    archive = (OUT / "06-eval-archive" / "project_archive_list.md").read_text(encoding="utf-8")
    for item in data["archive"]["items"]:
        check(item["path"] in archive, f"归档清单缺条目：{item['path']}")

    now = {k: sha(OUT / k) for k in data["inputs"] if (OUT / k).exists()}
    check(now == data["inputs"], "上游文件哈希变化：本技能不得修改上游")

    missing = [r for r in rows if r[7] == "待统计"]
    check(f"待统计 {len(missing)} 项" in report or not missing, "报告待统计数与台账不一致")

    print("PASS" if not ERR else "FAIL")
    for e in ERR:
        print(" -", e)


if __name__ == "__main__":
    main()
```

> 校验只读，不修改任何文件；失败时回到对应步骤修正，不降低校验口径。

## 附录 Z：实机回归失败模式与强制检查

> 来源：2026-11-16 首次在 PLCSIM Advanced 上真实执行 81 条用例（不是设计推演；项目与设备信息已脱敏），
> 结果 56 通过 / 25 不符。以下每条都由**真实失败**反推，不是假设。
> 编号规则在各技能内唯一，交付前逐条打勾；任一条不满足不得声明阶段完成。

### Z.1 归档哈希必须与内容一致（E-01 · 强制）

归档清单里的 SHA256 必须与实际文件一致。任何上游数据修订后，必须：

1. 升数据版本（如 DATA-V2.0 → V2.1）并写 `version_log`
2. 重算受影响文件的哈希，刷新归档清单与评估报告
3. 在评估报告的变更记录里注明"哪次修订、刷新了哪些快照"

> 真实事故：补录 13 行 BOM 关联后，归档清单与评估报告仍指向旧哈希与旧版本号，审计拿清单核文件直接失败。

### Z.2 "未执行"不得计入通过（E-02 · 强制）

评估指标里必须同时列出：执行覆盖率、通过率（分母=已执行）、未执行数。三者并列，禁止只给通过率。
> 真实事故：首版评估报告"仿真测试步骤通过率 未执行"，而综合追溯覆盖率写 100%，读者极易误读为"测试全过"。

### Z.3 快照过期必须显式登记（E-03 · 强制）

凡因上游修订而变得不一致的交付物，必须在报告里列成"过期快照清单"（文件 + 过期字段 + 刷新方式），不得留在文档里静默过期。
