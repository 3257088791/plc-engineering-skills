# 需求澄清与规格化（req-spec-01）

## 0. 目标与红线

把客户口语化、碎片化的原始要求，转成**可验证、可验收、可追溯**的需求规格；把必须问清楚才能成立的事项，转成**封闭式或半封闭式**澄清问题。

本技能只做到需求基线为止，**不进入下游设计**。

始终遵守以下红线：

1. **不编造**：不替客户拍板工艺参数、设备参数、量程、型号、阈值、精度、安全等级。信息不够就提问，或列入未决项。
2. **不落不可验收条目**：验收准则必须能用测试或观察判定；缺参数导致无法判定的，不写进规格表，留在澄清日志。
3. **固定字段、全局唯一 ID**：`REQ-ID | 需求内容 | 验收准则 | 优先级 | 关联IO占位 | 状态`，不多列、不少列、不改名；REQ-ID 跨轮次不重号、不复用。
4. **默认等待真实客户**：`auto_simulate_customer=false` 时，列出问题后停止，不生成规格表，不自行补参数。
5. **不越界**：不输出 IO 点表、地址、板卡、设备选型、控制方案、PLC 程序、HMI 画面、网络拓扑、BOM、电缆/端子设计。
6. **模拟不是确认**：模拟模式下所有依赖模拟回答的条目必须标注 `【模拟回答】`，日志逐条注明“模拟客户回答，非客户正式确认”，不得写成客户已确认。

**快速导航**：1 输入输出｜2 执行流程｜3 冲突处理｜4 隐含需求｜5 提问与追问｜6 续号与变更｜7 文件规范｜8 自检｜9 对话契约｜10 边界｜附录 A 日志模板｜附录 B 验收检查｜附录 C 模式速查

## 1. 输入、输出与模式

### 1.1 输入

至少读取并区分以下内容：

| 输入 | 作用 | 处理要求 |
|---|---|---|
| 客户原始文本 | 需求来源 | 口述、邮件、工单、会议纪要、聊天记录均可；保留原文，不先改写 |
| 工艺工况描述 | 约束与隐含需求来源 | 流程、工况条件、现场环境、上下游接口；只提取影响控制行为或验收的部分 |
| 既有规格表/日志 | 续号与跨轮追溯 | 存在则先读；不存在则从 `REQ-001` 开始 |
| 用户本轮指令 | 模式、优先级、补充答复 | 明确 `auto_simulate_customer` 取值；未说明按 `true` |

如果输入是多个文件或多段文本，先建立来源清单（文件名/段落/日期），后续每个候选条目都保留来源。

### 1.2 输出（路径固定）

| 文件 | 固定路径 | 生成时机 |
|---|---|---|
| 需求规格表 | `./output/requirements_spec.xlsx` | 澄清完成，或模拟模式完成一轮闭环后 |
| 澄清问答日志 | `./output/clarification_shturl.md` | 每轮都写；等待模式下也要写 |

注意：日志文件名中的 `shturl` 是需求指定的固定拼写，**不要改成 shorturl 或其他名字**。

等待模式下只生成/更新日志，**不生成规格表**。如果本轮没有任何待澄清问题，视为澄清已完成，可以直接生成规格表。

### 1.3 模式开关

从用户指令或调用参数读取布尔值 `auto_simulate_customer`：

| 取值 | 行为 |
|---|---|
| `false` | 列出问题 → 写入日志 → 停下来交给真实客户；不生成规格表，不补参数 |
| `true` （默认）| 列出问题 → 逐条模拟客户作答并标注 → 完成本轮闭环 → 生成规格表和日志 |

用户没有明确说“模拟客户/自动模拟/auto_simulate_customer=true”时，一律按 `true` 处理，不要猜测。

### 1.4 目录准备

先执行等价于下面的命令，确保输出目录存在：

```bash
mkdir -p ./output
```

Windows PowerShell 可用：

```powershell
New-Item -ItemType Directory -Force -Path .\output | Out-Null
```

然后再读写文件。不要先把文件写到别处再声称路径正确。

本技能不绑定具体工具名：使用宿主提供的文件读取、文件写入和 shell 工具即可（常见为 `read_file`、`write_file`、`bash`；本环境对应 `read`、`write`、`pwsh`）。

## 2. 执行流程

### 2.1 第一步：盘点输入，不做推断

1. 读取所有输入，记录来源、版本、日期。
2. 标出哪些是**客户明确要求**，哪些是**工艺背景/约束**，哪些是**第三方标准或既有系统事实**。
3. 检查是否具备最低信息：**控制对象、工艺目标、基本动作**。三者完全无法确定、且无法形成任何可验收条目时，停止并返回固定标记：

```text
【缺少参数：<具体缺什么>】
```

同时在日志中说明缺什么、为什么无法继续。不要用“常规做法”补齐后再生成规格表。

4. 读取既有 `./output/requirements_spec.xlsx` 和 `./output/clarification_shturl.md`（如果存在），确定下一个 REQ-ID、Q-ID、CON-ID 和轮次。读取规则见第 6.1 节。

### 2.2 第二步：拆成候选条目

把客户说的每一句话按语义拆开，而不是按标点机械切分。每个候选条目建立一条 C 记录：

| 字段 | 要求 |
|---|---|
| C-ID | `C-001`、`C-002`…，本轮内唯一；跨轮继续编号 |
| 原文 | 逐字引用，不改写；多段用 `…` 标省略 |
| 来源 | 文件名/段落/日期/说话人（可得时） |
| 候选内容 | 用“条件 + 对象 + 动作/指标”概括 |
| 初判 | 明确要求 / 工艺约束 / 背景信息 / 疑似缺陷 |

拆分规则：

- 一句话里如果有两个可独立验收的动作，拆成两条候选。
- 一句话里如果是一个完整顺序，先保留为一条候选，再判断是否需要按步骤拆分。
- 工艺背景（如“现场粉尘较大”）不自动变成需求；只有当它影响控制行为、防护动作或验收条件时，才转为约束或隐含需求候选。
- 客户已经给出明确数值和单位的，原样保留，不换算、不圆整、不“优化”。
- 客户没有给出的，标记“缺失”，不要用常识值填。
- 客户用“能不能/是否可以”提问时，先确认是否纳入本次范围（A 是/B 否/C 其他），不要直接写成需求。
- 客户说“最好/顺便/可选”时，追问是否本期必须及优先级；不要自动当成低优先级。

示例（仅示意格式，不表示任何真实项目参数）：

| C-ID | 原文 | 来源 | 候选内容 | 初判 |
|---|---|---|---|---|
| C-001 | “输送线要能自动运行” | 口述 §1 | 自动运行模式 | 缺触发条件、停止条件、模式定义 |
| C-002 | “卡料就停” | 口述 §1 | 卡料检测后停机 | 缺检测方式、确认时间、停机范围 |
| C-003 | “急停别忘了” | 口述 §1 | 急停功能 | 缺急停范围、复位方式、断电行为 |

### 2.3 第三步：四类问题逐条扫描

对每个候选条目，按下面四类逐一过一遍。**只记录真正影响需求内容或验收准则的问题**；不要为了凑数把所有通用检查项都列出来。

| 类型 | ID 前缀 | 判定问题 | 典型表现 | 处理 |
|---|---|---|---|---|
| 缺失信息 | `MIS-` | 做控制方案必须知道、但客户没说 | 对象不清、目标不清、触发/停止条件缺失、设定值/单位缺失、动作时间缺失、故障安全状态缺失、复位方式缺失、验收方法缺失 | 生成 1～3 个封闭问题；不得默认补值 |
| 矛盾描述 | `CON-` | 同一对象/同一条件下，两条说法不能同时成立 | 两个不同设定值、单位不一致、常开/常闭冲突、手动/自动互斥、顺序不可能、安全要求与操作要求打架 | 单独登记冲突；给选项；不选边 |
| 歧义描述 | `AMB-` | 一词多义、指代不明、范围不明、模糊措辞 | “自动”“正常”“及时”“快速”“稳定”“合理”“适当”“必要时”“联锁”“急停”“复位”“一批”“若干” | 要求客户选定义或填数值+单位 |
| 隐含需求 | `IMP-` | 客户没明说，但工艺、安全、联锁必然要求 | 急停/安全停、互锁、防干烧/防堵塞、断电恢复、传感器故障、通信丢失、手动维护模式、超时保护、数据保持 | 标为“候选隐含需求，待澄清”；只提问，不直接当成已确认需求 |

扫描时的最低检查维度（这些是自检提示，不是直接发给客户的问题；对外提问必须按 2.4 改写成选项或填数）：

1. **对象**：控制谁？检测谁？影响谁？
2. **目标**：达到什么状态、位置、速度、温度、压力、流量、节拍？
3. **条件**：什么信号/工况下开始、停止、切换、复位？
4. **量值**：设定值、阈值、公差、量程、单位。
5. **时间**：响应时间、确认时间、超时时间、保持时间、周期。
6. **异常**：传感器故障、执行机构故障、卡料/堵塞、超限、通信丢失时进入什么状态？
7. **安全**：急停、安全停、联锁、断电/恢复、人工复位。
8. **模式**：手动/自动、单步/连续、本地/远程如何切换和互锁？
9. **验收**：用什么输入、观察什么输出、允许误差/动作时间、重复多少次？
10. **权限与记录**：谁可操作、谁可复位、是否记录、记录哪些字段、保存多久？

**不要**把“设备选型、PLC 型号、IO 点数、板卡、量程选型、网络协议、HMI 画面布局”当作需求澄清问题；这些是下游设计。若客户已明确给出某项作为约束，只记录约束，不展开设计。

### 2.4 第四步：生成澄清问题

每个待澄清点生成 **1～3 条**具体问题；超过 3 条说明问题没拆清，先拆成多个问题点。

问题必须满足：

- **封闭式或半封闭式**：给出可选项，或给出“填写数值 + 单位”的明确空格。
- **可直接回答**：客户不用再反问“你指的是什么”。
- **带影响**：说明会影响哪条候选/哪条验收。
- **不重复**：客户已经说过的，不再问。
- **不越界**：不问下游选型与设计细节。
- **不诱导**：选项要平衡；不要只给一个明显“正确”的选项。

推荐模板：

```text
Q-001（对应 MIS-001，影响 C-002 / REQ 候选）：
<对象>在<条件>下应<动作>？
A. <选项 1，带数值和单位>
B. <选项 2，带数值和单位>
C. <选项 3，带数值和单位>
D. 其他：请填写<具体对象/数值+单位>
```

数值型模板：

```text
Q-002（对应 MIS-002，影响 C-004 的验收准则）：
请填写<参数名>的要求值：______ <单位>。
若按现有工艺分档，可选：A. ≤____；B. ____～____；C. ≥____；D. 其他（填写数值+单位）。
```

是/否型模板：

```text
Q-003（对应 IMP-001，影响 C-003 的故障行为）：
<条件>发生时，是否要求<动作>？
A. 是，要求<动作>；B. 否，不要求；C. 仅<部分对象>要求；D. 其他（请说明对象）。
```

常见提问种子（**只在相关时使用，禁止机械全套提问；每条都要落成选项或“____ + 单位”**）：

| 场景 | 可用的封闭/半封闭问法（按需拆成 1～3 条） |
|---|---|
| 启动/停止 | 启动方式：A. 点动；B. 单次循环；C. 连续运行；D. 其他（填写____）。停止方式：A. 立即切断输出；B. 减速停；C. 保持当前位置；D. 其他（填写____）。 |
| 自动模式 | “自动”指：A. 单次循环；B. 连续运行；C. 按节拍逐次启动；D. 其他（填写____）。退出自动的条件：A. 按停止；B. 故障；C. 模式开关；D. 其他（填写____）。 |
| 设定值/误差 | 目标值 ____ `<单位>`；允许误差：A. ±____ `<单位>`；B. ≤____ %FS；C. 其他（填写____）。 |
| 动作时间 | 从 `<起点>` 到 `<终点>` 的最大允许时间 ____ s；计时起点：A. 信号有效沿；B. 操作按下；C. 其他（填写____）。 |
| 卡料/堵塞 | 判定信号：A. 现有传感器；B. 电机电流；C. 人工确认；D. 其他（填写____）。确认时间 ____ s。停机范围：A. 单轴；B. 整线；C. 全部输出；D. 其他（填写____）。 |
| 急停 | 切断范围：A. 全部输出；B. 仅危险轴；C. 其他（填写____）。停止方式：A. 保持抱闸/制动；B. 自由停；C. 其他（填写____）。复位：A. 手动；B. 自动；C. 其他（填写____）。 |
| 联锁 | 互锁对象：A. `<对象1>`；B. `<对象2>`；C. 其他（填写____）。解除条件：A. 安全门关闭；B. 人工复位；C. 其他（填写____）。 |
| 断电恢复 | 恢复供电后：A. 禁止自动重启，人工确认；B. 按原状态恢复；C. 其他（填写____）。 |
| 传感器故障 | 断线/超量程/无变化时：A. 保持并报警；B. 停止相关对象并报警；C. 停止全部输出并报警；D. 其他（填写____）。 |
| 通信丢失 | 判定时间 ____ s；进入状态：A. 保持；B. 停止相关对象；C. 停止全部输出；D. 其他（填写____）。恢复：A. 自动；B. 人工确认；C. 其他（填写____）。 |
| 报警触发 | 报警条件：A. `<条件1>`；B. `<条件2>`；C. 其他（填写____）。确认延时 ____ s。 |
| 报警复位/记录 | 复位：A. 自动；B. 手动；C. 其他（填写____）。记录字段：A. 时间；B. 设备；C. 报警码；D. 其他（填写____）；保存 ____ 天。 |
| 权限 | 需要权限的操作：A. 参数修改；B. 手动动作；C. 报警复位；D. 其他（填写____）。权限形式：A. 密码；B. 钥匙；C. 管理员登录；D. 其他（填写____）。 |
| 验收 | 输入激励：A. `<激励1>`；B. `<激励2>`；C. 其他（填写____）。观察输出：A. `<输出1>`；B. `<输出2>`；C. 其他（填写____）。重复 ____ 次，允许失败 ____ 次。 |

问题质量的反例：

- 反例：“请补充工艺参数。”——开放式大问，无法直接回答。
- 反例：“急停是不是要切断全部输出？”——只给一个诱导性选项；应给出“全部/危险轴/其他”的选项。
- 反例：“响应时间按常规就行吧？”——把拍板权拿回自己手里，违反不编造。
- 反例：“PLC 用哪个型号？”——下游选型，越界。

### 2.5 第五步：按开关分流

#### A. `auto_simulate_customer=false`

1. 把本轮识别出的候选、四类问题、澄清问题写入 `clarification_shturl.md`。尚未回复的 Q，回复列写“待客户回复”，结论列写“未落地-待回复”。
2. **不要**生成或修改 `requirements_spec.xlsx`。
3. **不要**自行补全任何缺失参数。
4. 在对话中给出简短摘要：识别到多少待澄清点、多少个问题、日志路径；请客户按 Q-ID 回复。
5. 停下来等待。客户未回复前，不进入规格化。

本轮没有任何待澄清问题时，跳过等待，直接进入规格化；但仍要在日志中写“本轮无需澄清”及依据。

#### B. `auto_simulate_customer=true`（默认）

1. 先按前述流程列出问题。
2. 逐条扮演客户作答；每条回复前加固定标注：

```text
【模拟客户回答，非客户正式确认】
```

3. 模拟回答必须：
   - 基于已有输入、工艺常识和保守的工程取值；每条回复在标注后注明依据（引用 C-ID 或说明“保守取值”），不得只甩一个数；
   - 不与管理已确认的条目矛盾；
   - 不编造具体设备型号、传感器量程/精度、安全完整性等级、材料牌号；这些属于硬性约束 1 的禁用项，模拟模式也不能编，只能作为未决项；
   - 对安全相关行为优先选择失效安全、人工复位、禁止自动重启；
   - 对无法保守推导的具体参数，回答“需客户确认”，并让依赖它的条目保持未决，不落表；
   - 数值必须带单位，且与工艺量级相符；明显离谱的取值禁止使用；
   - 不把“模拟选择”写成“客户确认”。
4. 完成本轮问答闭环（每个 Q 都有模拟回复，或明确标为“需客户确认”）后，生成日志和规格表；无法落表的条目留在日志未决项。
5. 所有依赖模拟回答的 REQ，状态一律写 `【模拟回答】`；直接来自客户原文、未依赖模拟回答的条目可按证据写 `已确认`。
6. 在对话结尾明确说明：本轮包含模拟客户回答，不是客户正式确认，需真实客户复核。

模拟模式不是“可以随便编”的许可。它模拟的是**客户的选择**，不是把未知事实伪装成已知事实。无法可靠模拟的，仍然留空、留问题、留日志。

### 2.6 第六步：写需求条目

#### 2.6.1 原子性

一条 REQ 只表达一个可独立验收的行为或指标。以下情况拆条：

- 两个对象各自独立动作；
- 两个独立报警条件；
- 两个不同工况下的不同设定值；
- 安全联锁与显示/记录混在一条。

一个完整顺序如果必须整体验收，可以保留为一条，但验收准则要逐步可判定。

#### 2.6.2 需求内容

一句话说清“在什么条件下、对什么对象、做什么动作/达到什么指标”。

推荐句式：

```text
在<模式/工况/条件>下，当<触发/输入>成立时，<对象>执行<动作>，达到<状态/位置/指标>。
```

要求：

- 不用“应该”“尽量”“适当”“合理”等留口子的词。
- 不把验收阈值重复两遍；阈值放验收准则，需求内容保留目标。
- 不写实现方式（用哪个继电器、哪张卡、哪段程序）。
- 客户原话中的关键限定（模式、对象、方向、优先级）不能丢。

#### 2.6.3 验收准则

每条都必须写成可执行、可判定的形式，至少包含：

1. **测试前置条件**（模式、初始状态、物料/负载、环境，如相关）；
2. **输入 X**（信号、操作、扰动、故障注入，含持续时间/幅值/单位）；
3. **输出 Y**（哪个对象、什么状态/数值、在哪里观察）；
4. **判定阈值 Z**（误差、动作时间、超时、重复次数、通过标准，含单位）；
5. **通过/失败规则**。

推荐骨架：

```text
在<前置条件>下，输入<X，含幅值/持续时间/单位>时，<输出 Y>应在 ≤ <Z，含单位> 内达到<目标状态/数值>；重复<n>次，<n>/<n>次满足则通过，否则失败。
```

按需求类型的可用骨架（尖括号为待填参数，**不得原样落表**）：

| 类型 | 验收准则骨架 | 必须补齐 |
|---|---|---|
| 开关量动作 | 当 `<信号>` 由 `<0/1>` 变为 `<1/0>` 时，`<输出>` 在 ≤ `<t> s` 内变为 `<状态>`；重复 `<n>` 次，`<n>/<n>` 通过 | 信号定义、输出对象、t、n |
| 模拟量调节 | 在 `<模式>` 下，`<被控量>` 保持在 `<设定值 ± 公差> <单位>` 的带内；施加 `<扰动>` 后，在 ≤ `<t> s` 内恢复到该带内 | 设定值、公差、单位、扰动、t |
| 联锁/急停 | 当 `<条件>` 成立时，`<对象>` 在 ≤ `<t> s` 内 `<停止/切断/保持>`；条件保持 `<T> s` 期间输出不得恢复 | 条件、对象、t、T、复位方式 |
| 报警 | 当 `<条件>` 持续 `<t1> s` 时，`<报警>` 置位；条件消失后 `<t2> s` 内复位；记录包含 `<字段>` | t1、t2、字段、复位方式 |
| 顺序动作 | 在 `<启动条件>` 下，按 `<步骤 1→2→…>` 执行；每步 ≤ `<t> s`，整周期 ≤ `<T> s`；任一步超时进入 `<安全状态>` | 步骤、t、T、安全状态 |
| 显示/记录 | `<显示/记录项>` 与 `<实际值>` 的绝对偏差 ≤ `<值> <单位>`；刷新/写入周期 ≤ `<t> s`；`<n>` 次变化中 `<n>/<n>` 正确 | 项目、误差、周期、n |

硬性要求：

- 所有物理量必须带单位；计数、次数、百分比用“次/个/%”等明确量纲，不写裸数。
- 误差写成 `±<值> <单位>` 或 `≤ <值> %FS`，并说明参照量程。
- 动作时间要说明计时起点和终点，例如“从信号有效沿到输出触点闭合”。
- 不允许出现“运行稳定”“响应及时”“较好”“较快”“合理”“适当”“满足工艺要求”“正常工作”“必要时”“视情况”等无法判定的表述。
- 不允许在验收准则里写“待确认”“见日志”“按现场情况”。参数不全就不落这条 REQ，把它留在日志。
- 不允许把“设备选型/精度选型”写成验收条件；可以写“以 PLC 内部变量为准”“以现场检测元件读数为准”等观察基准，但不指定型号。

好/坏示例（**尖括号内是待填参数，不是可抄的数值**）：

| 反例 | 问题 | 改法 |
|---|---|---|
| 需求：系统运行稳定，响应及时。验收：运行稳定，响应及时。 | 两个模糊词，无法判定 | 改成“在 `<工况>` 下连续运行 `<T> h` 无 `<指定报警>`；从 `<输入>` 到 `<输出>` 的动作时间 ≤ `<t> s`” |
| 需求：卡料就停。验收：卡料时停机。 | 缺检测方式、确认时间、停机范围 | 先问清“卡料信号是什么、持续多久确认、停哪些对象”，再写成带 t 和对象的验收 |
| 需求：急停切断设备。验收：急停有效。 | 缺范围、复位、保持行为 | 先问清“切全部还是危险轴、是否保持制动、如何复位”，再写联锁验收 |

#### 2.6.4 优先级

| 优先级 | 适用 |
|---|---|
| 高 | 安全、联锁、急停、失效安全、人身/设备保护类 |
| 中 | 常规工艺控制、顺序、调节、影响工艺但非安全类的报警 |
| 低 | 操作优化、显示、记录、运维便利类 |

客户明确指定优先级时，以客户输入为准。客户使用 `P0/P1/P2`、`A/B/C` 等优先级标签时，原样保留客户标签，并在日志中注明映射关系；不要擅自改级。若一条需求同时包含安全与显示，拆成两条，分别定级。

#### 2.6.5 关联 IO 占位

只允许：

- 留空；或
- 写 `TBD`。

禁止写任何真实点位、地址、板卡、通道、机架、DB 号、符号表地址，例如 `I0.0`、`Q0.0`、`%IW64`、`DB1.DBX0.0`、`AI 通道 3`。也不要在日志里“顺便”分配地址。

#### 2.6.6 状态

| 状态 | 使用条件 |
|---|---|
| `待澄清` | 需求内容与验收准则已经完整可测，但客户尚未最终确认，或客户明确要求先落表待签；**缺参数导致无法判定时不得用本状态落表**，应留在日志 |
| `已确认` | 客户原话明确，或客户在澄清轮中明确确认 |
| `已关闭` | 客户确认关闭、需求已撤销、已被后续条目替代；不表示已完成下游验收测试；日志必须写明原因 |
| `【模拟回答】` | 模拟模式下，凡依赖模拟回答生成的条目一律使用；这是状态列的固定例外。在模拟轮次内不得改为 `已确认`；后续真实客户确认按 6.2 另起一轮处理 |

状态变更要留痕：不要静默改写历史。客户后续给出真实答复时，新增一轮日志；确认无误的模拟条目可改为 `已确认`，内容有变的应关闭旧 REQ 并新增 REQ，不重用旧号。

### 2.7 第七步：写澄清日志

日志必须按轮次追加，不覆盖历史。每轮至少包含：

1. 输入拆分与候选条目；
2. 四类问题清单；
3. 澄清问答（问题 → 回复 → 结论 → 落地 REQ-ID）；
4. **冲突单独登记**（没有也要写“本轮未发现冲突”）；
5. 本轮结论与未决项；
6. 模拟声明（仅模拟模式）；
7. 追溯矩阵（C → Q → REQ）。

允许每轮更新文件顶部的“当前状态”摘要；历史轮次的正文只能追加，不得改写。

日志模板见附录 A。要求：

- 已完成的轮次中，每条 Q 都必须有回复、结论，以及“落地到哪条 REQ-ID”或“未落地/待裁决”的明确说明；不允许有头无尾。等待模式下尚未回复的 Q，回复列写“待客户回复”，结论列写“未落地-待回复”，并列入未决项。
- 每条 REQ 都必须能追溯到至少一个 C-ID（隐含需求可同时关联 IMP-ID）；经过澄清的还要关联 Q-ID，未经澄清的写“无需澄清/直接来自原文”。没有来源的条目不得写入规格表。
- 冲突不能埋在问答表格里，必须单独成节/成表，写清：涉及哪两条原始描述、冲突内容、待客户裁决的选项、当前状态。
- 模拟回复逐条带 `【模拟客户回答，非客户正式确认】` 标注。
- 不写真实 IO 地址、设备型号、控制方案。

### 2.8 第八步：自检后交付

按第 8 节清单自检；不通过就修正。无法修正的，明确报告，不假装完成。

## 3. 矛盾处理（必须单独登记）

发现矛盾时：

1. 不要选边，不要用“取中间值”“按常规”等方式私自消解。
2. 在日志中单独建立 `CON-xxx` 记录，至少包含：

```markdown
### 冲突 CON-001

- 原始描述 A：C-003「<逐字原文>」
- 原始描述 B：C-007「<逐字原文>」
- 冲突内容：<同一对象/条件下，A 要求…，B 要求…，不能同时成立>
- 影响：<影响哪些候选/验收/安全行为>
- 待客户裁决的选项：
  - A. <具体方案/数值+单位>
  - B. <具体方案/数值+单位>
  - C. <其他，请填写具体对象/数值+单位>
- 客户裁决：待裁决 / 已裁决（模拟） / <客户选择>
- 落地：未落地 / REQ-xxx
```

3. 未裁决前：
   - 不把冲突中的任一数值写成正式 REQ；
   - 不把带冲突的条目标成 `已确认`；
   - 在日志“未决项”中列出。
4. 模拟模式下，模拟客户可以选择一个选项，但必须标注为模拟裁决，相关 REQ 状态为 `【模拟回答】`；不得写成客户正式裁决。
   - 同时在日志的 `客户裁决` 字段写 **`已裁决（模拟）`**，并紧跟一行 `【模拟裁决】依据：…；风险：…`。
   - 严禁把已模拟裁决的冲突继续写成 `待裁决`：上游编排层按“日志中是否出现 `已裁决（模拟）`”判断是否阻塞（见 auto-flow-master-00 §G1-05.5）。
   - 选项本身仍必须包含失效安全方案，且模拟裁决不得降低安全要求（不得为了通过而选更宽松的选项）。
5. 如果冲突涉及安全与生产、急停范围、联锁解除条件，选项必须包含失效安全方案；仍然不替客户选。

常见冲突类型：

- 同一参数两个值/两个单位；
- “手动可点动”与“强制互锁”范围不清；
- 急停“切断全部”与“只停危险轴”；
- 自动模式下允许人工干预，但安全要求禁止；
- 先开门后停机与先停机后开门；
- 断电恢复自动运行与防意外启动；
- 报警后自动复位与人工确认。

## 4. 隐含需求的边界

隐含需求只能作为**候选**提出，不能直接当成客户已确认的需求。只有工艺、设备或安全链明确涉及时才提；不要机械罗列通用安全条款。

可以推导的典型方向：

- 急停/安全停后的输出状态与复位方式；
- 运动机构之间的互锁与先后条件；
- 卡料、堵塞、超温、超压、超限、断线、无变化等故障检测；
- 断电/恢复、通信丢失、传感器故障时的安全状态；
- 手动维护模式下的禁止自动启动；
- 超时保护与故障保持；
- 报警记录、操作记录、权限。

提问方式示例：

```text
Q-004（对应 IMP-001，影响 C-006 的安全行为）：
当<故障/通信丢失/传感器断线>发生时，系统应进入哪种状态？
A. 保持当前动作并报警；
B. 停止相关对象并报警，等待人工复位；
C. 停止全部输出并报警，等待人工复位；
D. 其他：请说明对象与复位方式。
```

不要写“必须符合相关安全标准”而不给标准号/条款；也不要自行指定安全等级。客户未给出时，作为待澄清项。

## 5. 问题质量与追问规则

### 5.1 合格问题

- 一个问题只问一个决策点。
- 选项互斥、覆盖主要可能，并留“其他（请填写…）”。
- 数值选项带单位；范围选项写清边界。
- 说明影响，方便客户判断优先级。
- 能在客户现有知识范围内回答，不要求客户做下游设计。

### 5.2 追问

客户回复后：

1. 先把回复映射到 Q-ID。
2. 检查是否回答了问题；如果只是“按常规”“你定”“差不多”，视为未回答，继续追问具体值/选项。
3. 如果回复引入新矛盾，登记新的 `CON-xxx`，不要静默覆盖旧说法。
4. 如果回复仍缺单位/对象/条件，只追问缺的那一项，不要重复整份问题。
5. 客户只给范围时，追问目标设定值和允许误差；不要拿范围中值当设定值。
6. 所有 blocking 问题解决后，才进入规格化；未解决项留在日志，不写成不可验收的 REQ。

### 5.3 不要问的情况

- 客户已经明确给出答案；
- 答案不影响需求内容或验收准则；
- 属于下游设计（选型、点位、程序、画面、网络）；
- 只是为了让表格“看起来完整”；
- 客户无法回答、且不影响当前基线：记录为日志中的假设/待定项，不能写成已确认；若它影响验收准则，则不落表。

## 6. 需求变更与跨轮续接

### 6.1 续号

- REQ-ID 全局唯一，跨轮次不重号、不复用。
- 读取已有 `./output/requirements_spec.xlsx`，取所有工作表中出现的最大 `REQ-<数字>`，下一条为 `max + 1`。
- 文件不存在时从 `REQ-001` 开始。
- 至少补足 3 位：`REQ-001`…`REQ-999`，之后 `REQ-1000`；不要回绕。
- 即使中间有缺口，也不要用缺口号；只取最大值续号。
- 已有 ID 保持原样，不重新编号；新 ID 以文本格式写入，保留前导零。

Q-ID、C-ID、CON-ID、MIS/AMB/IMP-ID 同样跨轮续号：读取日志中上一轮的最大编号，取 `max + 1`；无日志时从 `001` 开始。

### 6.2 变更

- 需求内容变化：关闭旧 REQ（`已关闭`，日志写原因），新增 REQ；不复用旧号。
- 只是状态确认：在原 REQ 上更新状态，并在新轮次日志记录“由谁/哪条回复确认”。
- 模拟条目被真实客户明确确认后，才可更新为 `已确认`；必须新增一轮日志，记录确认来源。若真实答复与模拟值不同，按内容变更处理：关闭旧 REQ，新增 REQ。
- 删除需求：不要物理删除历史行；标 `已关闭` 并说明撤销/替代关系。

### 6.3 文件不存在/格式异常

- 规格表不存在：新建，表头严格为六字段，从 `REQ-001` 开始。
- 规格表存在但表头不符、ID 重复、无法解析：**停止写入**，保留原文件，在回复中报告具体问题；不要覆盖、不要“顺手修正”。
- 日志不存在：新建；存在：读取最后一轮和最大编号后追加。
- 输出目录不存在：先创建。

## 7. 输出文件规范

### 7.1 requirements_spec.xlsx

硬性结构：

- 真实 `.xlsx` 文件，优先用 `python3`（Windows 无 `python3` 时用 `python`）+ `openpyxl` 生成；禁止把 CSV/HTML 改扩展名。
- 新建时只放一张需求表（工作表名可用 `需求规格`）；已有文件若含多张表，读取所有表续号，但只向表头匹配的那张追加；多张都匹配或无法判断时停止并报告，不擅自合并或删除。
- 第 1 行是表头，必须**逐字**为：

```text
REQ-ID | 需求内容 | 验收准则 | 优先级 | 关联IO占位 | 状态
```

- 第 2 行起是数据；不要标题行、说明行、合并单元格、空列、额外列。
- 不要加“来源”“验收方法”“备注”等列；追溯信息放日志。
- `REQ-ID` 用文本格式，保留前导零。

最小生成骨架（只负责写表，不涉及控制逻辑；按单表场景编写，多表场景先按表头定位需求表再追加）：

```python
from pathlib import Path
import os
import re
from openpyxl import Workbook, load_workbook
from openpyxl.styles import Alignment, Font, PatternFill

HEADERS = ["REQ-ID", "需求内容", "验收准则", "优先级", "关联IO占位", "状态"]


def max_req_id(path: Path) -> int:
    if not path.exists():
        return 0
    wb = load_workbook(path, read_only=True, data_only=False)
    mx = 0
    for ws in wb.worksheets:
        for row in ws.iter_rows(values_only=True):
            for value in row:
                if isinstance(value, str):
                    m = re.fullmatch(r"REQ-(\d{3,})", value.strip())
                    if m:
                        mx = max(mx, int(m.group(1)))
    wb.close()
    return mx


def load_or_create(path: Path):
    if path.exists():
        wb = load_workbook(path)
        matches = []
        for ws in wb.worksheets:
            header = [ws.cell(1, c).value for c in range(1, 7)]
            if ws.max_column == 6 and header == HEADERS:
                matches.append(ws)
        if len(matches) != 1:
            raise ValueError("现有工作簿中未找到唯一一张六字段需求表，停止写入")
        return wb, matches[0]

    wb = Workbook()
    ws = wb.active
    ws.title = "需求规格"
    ws.append(HEADERS)
    for c in range(1, 7):
        cell = ws.cell(1, c)
        cell.font = Font(bold=True)
        cell.alignment = Alignment(horizontal="center", vertical="center", wrap_text=True)
        cell.fill = PatternFill("solid", fgColor="D9E2F3")
    for col, width in {"A": 12, "B": 44, "C": 60, "D": 8, "E": 14, "F": 12}.items():
        ws.column_dimensions[col].width = width
    ws.freeze_panes = "A2"
    return wb, ws


def append_requirements(path: Path, rows: list[dict]):
    # rows 的键：需求内容、验收准则、优先级、关联IO占位、状态
    path.parent.mkdir(parents=True, exist_ok=True)
    wb, ws = load_or_create(path)

    existing_ids = [
        ws.cell(r, 1).value
        for r in range(2, ws.max_row + 1)
        if ws.cell(r, 1).value not in (None, "")
    ]
    normalized_ids = []
    for value in existing_ids:
        m = re.fullmatch(r"REQ-(\d{3,})", value.strip()) if isinstance(value, str) else None
        if not m:
            raise ValueError("现有 REQ-ID 格式不符，停止写入")
        normalized_ids.append(int(m.group(1)))
    if len(normalized_ids) != len(set(normalized_ids)):
        raise ValueError("现有 REQ-ID 存在重复，停止写入")

    start = max_req_id(path) + 1

    for offset, row in enumerate(rows):
        values = [f"REQ-{start + offset:03d}"] + [row[h] for h in HEADERS[1:]]
        ws.append(values)
        for cell in ws[ws.max_row]:
            cell.alignment = Alignment(vertical="top", wrap_text=True)
        ws.cell(ws.max_row, 1).number_format = "@"

    ids = [
        ws.cell(r, 1).value
        for r in range(2, ws.max_row + 1)
        if ws.cell(r, 1).value not in (None, "")
    ]
    if len(ids) != len(set(ids)):
        raise ValueError("REQ-ID 存在重复，停止写入")

    ws.auto_filter.ref = f"A1:F{ws.max_row}"
    tmp = path.with_name(path.stem + ".tmp" + path.suffix)
    wb.save(tmp)
    wb.close()
    os.replace(tmp, path)
```

## 附录 Z：实机回归失败模式与强制检查

> 来源：2026-11-16 首次在 PLCSIM Advanced 上真实执行 81 条用例（不是设计推演；项目与设备信息已脱敏），
> 结果 56 通过 / 25 不符。以下每条都由**真实失败**反推，不是假设。
> 编号规则在各技能内唯一，交付前逐条打勾；任一条不满足不得声明阶段完成。

### Z.1 故障与业务拒绝必须分开（R-01 · 强制）

需求里凡出现"满/无车/超限/未授权/未支付"这类**业务拒绝**条件，必须与"急停/过载/断线/超时"这类**设备故障**分开写，并各自给出后果：

| 类别 | 允许的后果 | 禁止的后果 |
|---|---|---|
| 设备故障（fault） | 锁存、停机、需人工复位 | — |
| 业务拒绝（rejection） | 仅拒绝本次操作，其余功能照常 | **不得锁存、不得置故障有效位、不得禁全局动作** |

> 真实事故：把"业务拒绝（容量已满）"并入故障锁存，导致容量超限后**业务功能整体瘫痪**。

### Z.2 上电初始状态与复位策略（R-02 · 强制）

每条涉及锁存的需求，必须写明三件事，缺一不可：
1. **上电首扫描的行为**：输入全 0 时是否会被判成"动作"（真实事故：首扫描 I=0 → 急停/过载被判为动作，一上电就报故障）
2. **谁能复位**：按钮点位 + 权限等级 + 复位时必须同时满足的条件
3. **复位后哪些量归零**：步序、锁存、统计计数、请求寄存器

### Z.3 变量的读写归属（R-03 · 强制）

每个"模式/权限/参数/累计值"必须标明 **谁写、谁读**。同名变量既当 HMI 输入又当显示位的，必须在需求阶段拆成两个。
> 真实事故：`HMI_ModeSelect` / `HMI_UserLogin` 被程序当输入读、又被当作显示位，外部无法设定模式与权限，导致所有自动流程用例无法启动。

### Z.4 验收准则必须"可判定"（R-04 · 强制）

每条验收准则必须能落成 `观测点 + 比较方式 + 判定时刻` 三元组；只写"应正常/应有效/应无误"的，退回重写。
