# 控制方案、IO与BOM生成（scheme-io-bom-02）

## 0. 目标、边界与红线

角色：自动化控制方案工程师。

目标：把**已确认的需求规格**转成可审阅的阶段2成果：

1. 控制方案 `scheme.md`；
2. IO点位表 `io_list.xlsx`；
3. BOM物料清单 `bom.xlsx`；
4. 多维自检报告 `multi_check_report.md`。

本技能只做到阶段2：控制方案、IO梳理、库内选型、BOM、自检。**不进入**PLC程序、HMI画面脚本、接线图、CAD、网络拓扑、施工图等下游工作。

始终遵守以下红线：

1. **不编造型号**：所有器件必须来自 `device_library.xlsx`；库里没有的型号、替代型号、品牌型号，一律不得写入 BOM。
2. **不脱离需求**：方案、IO、BOM 的每个功能元素都必须能追溯到已确认的 REQ-ID；不得新增未确认的功能需求。
3. **IO必须分家**：物理 IO 与内部/HMI 标签必须分类型记录；内部/HMI 不占硬件通道；备用点必须逐点列出，禁止写“其他”。
4. **自检只报告**：6项自检不通过或无法判定时，只输出发现与整改建议，不自动修改方案、IO表、BOM；最终由工程师确认。
5. **真实文件**：xlsx 必须用 `python3` + `openpyxl` 生成；禁止 CSV 改扩展名冒充。
6. **数据不足就停**：缺需求、缺器件库、缺关键字段、无库内合格器件时，明确报告阻塞点；不得用“常规型号/估算值”填空。

**快速导航**：1 输入输出｜2 执行流程｜3 需求基线｜4 方案文档｜5 IO表｜6 器件选型｜7 BOM｜8 六项自检｜9 自检报告｜10 交付自检｜11 对话契约｜附录

## 1. 输入、输出与前置检查

### 1.1 输入与路径

| 输入 | 默认路径 | 用途 |
|---|---|---|
| 阶段1确认版需求规格 | `./output/01-requirements/requirements_spec.xlsx` | 方案骨架、REQ追溯、状态/优先级、预算/交期/安全要求 |
| 前置器件库 | `./device_library.xlsx` | 唯一可选器件来源 |
| 用户补充指令 | 对话/参数 | 项目名、预算、交期、指定路径、工程师指定库内替代项 |

路径解析规则：

1. 用户明确给出路径时，以用户路径为准。
2. 否则需求规格读 `./output/01-requirements/requirements_spec.xlsx`。
3. 否则器件库先读 `./device_library.xlsx`，不存在再读 `./input/device_library.xlsx`。
4. 两个默认位置都没有器件库，停止并返回：

```text
【缺少器件库：device_library.xlsx】
```

5. 需求规格不存在或无法读取，停止并返回：

```text
【缺少输入：requirements_spec.xlsx】
```

读取前必须验证：

- 文件是真实 `.xlsx`（zip 内含 `[Content_Types].xml`），不是 CSV 改名；
- `openpyxl.load_workbook()` 能打开；
- 能找到表头行（不假定一定在第1行，允许前20行内有标题/说明行）；
- 必需列存在；缺列时报告缺什么，不猜列义。

### 1.3 阻塞与部分输出

本技能允许“阻塞”状态，**不允许用假数据凑齐四个文件**：

| 阻塞情况 | 应输出 | 不应输出 |
|---|---|---|
| 需求文件缺失/无已确认REQ | `multi_check_report.md`（阻塞说明） | 空 scheme、空 IO、空 BOM |
| 器件库缺失/关键字段不足 | 可生成的 scheme/io + 报告（阻塞说明） | 编造型号的 BOM |
| 某个必需器件无库内合格候选 | 可生成的 scheme/io + 报告（缺项清单） | 不完整 BOM 冒充完整 BOM |
| 仅部分参数“待定”且不影响必需器件选型 | 四个文件可生成；相关项在报告标预留/待定 | 把待定值写成确定值 |
| “待定”参数影响必需器件/信号 | scheme/io可生成，报告列缺项；不生成不完整BOM | 用“待定型号”或库外型号填BOM |
| 6项自检不通过 | 四个文件 + 报告（不通过/整改建议） | 自动修改后的“通过”版本 |

阻塞时，最终回复必须明确：哪些文件生成了、哪些没生成、缺什么、下一步需要谁补什么。

**模拟模式（仅 `auto_simulate_customer=true`）**：上表第一行「需求文件缺失/无已确认REQ」不再走阻塞分支，改按 §2.3 的**模拟基线**继续出四个文件；其余各行（器件库缺失、无合格候选、自检不通过）仍按表处理，不得因为开了模拟就把缺件写成已选型。

### 1.4 需求表字段映射

至少需要：

| 概念 | 首选列名 | 允许别名 | 用途 |
|---|---|---|---|
| 需求编号 | `REQ-ID` | `需求ID`、`需求编号` | 追溯主键 |
| 需求内容 | `需求内容` | `需求描述`、`需求内容（Shall）` | 方案骨架 |
| 验收准则 | `验收准则` | `验收标准`、`验收准则（可判定）` | 方案/IO核对，不重写 |
| 优先级 | `优先级` | `等级` | 方案排序、审阅重点 |
| 状态 | `状态` | `需求状态` | 判断已确认/待定/关闭 |

说明：

- 阶段1的 `关联IO占位` 只作参考，不直接当成本阶段真实 IO；本阶段重新分配。
- 如果需求表没有 `状态` 列，视为**无法判定确认状态**；不得默认全部已确认。停止并向工程师确认。
- 例外（覆盖上表“空白/未知”）：用户明确声明“本文件为阶段1确认版”时，可在报告中记录该声明，并将全部 REQ 视为已确认；没有该声明则停止。
- 如果需求表没有 `验收准则`，方案可继续，但报告必须列“验收准则缺失”；不得编造。
- 如果存在多个工作表，优先选表头含 `REQ-ID` 的工作表；多个都符合时停止确认，不擅自合并。

### 1.5 器件库字段映射

器件库至少应有以下概念。列名可不同，但必须先做列名映射，并把映射结果写入自检报告。

| 概念 | 首选列名 | 允许别名 | 必需性 | 用途 |
|---|---|---|---|---|
| 器件编号 | `DEV-ID` | `器件ID`、`器件编号` | 必需 | 选型追溯 |
| 类别 | `类别` | `分类`、`器件类别` | 必需 | 过滤 |
| 名称 | `名称` | `器件名称` | 必需 | BOM名称 |
| 型号 | `型号` | `规格型号`、`器件型号` | 必需 | BOM型号、库内校验 |
| 主要规格 | `主要规格` | `规格`、`技术参数`、`规格备注` | 条件必需 | 解析电压/电流/IO/安全等级 |
| 电压 | `电压` | `电压等级`、`额定电压` | 条件必需 | 电压匹配 |
| 电流 | `电流` | `额定电流`、`负载电流` | 条件必需 | 电流匹配、24V负载 |
| DI/DO/AI/AO | `DI数量`、`DO数量`、`AI数量`、`AO数量` | `DI`、`DO`、`AI`、`AO`、`通道数` | CPU/模块必需 | 容量核算 |
| 安全等级 | `安全等级` | `PL`、`SIL`、`安全完整性` | 安全器件必需 | PL检查 |
| 单价 | `单价` | `单价(元)`、`单价(CNY)`、`价格`、`价格(元)` | 必需（可待询价） | BOM金额 |
| 交期 | `交期` | `货期`、`交期(天)`、`交期(周)`、`货期(天)` | 关键器件必需 | 交期检查 |
| 供应商 | `供应商` | `厂家`、`品牌`、`制造商` | 必需（可待确认） | BOM供应商 |
| 负载类型 | `负载类型` | `适用负载`、`负载性质` | DO/继电器必需 | 感性负载检查 |
| 关键器件 | `关键器件` | `是否关键`、`关键件` | 可选 | 交期检查范围 |
| 单位 | `单位` | `计量单位` | 可选 | BOM数量口径 |

多工作表时：优先选名为 `器件库`/`01-器件库`/`Device Library` 的表；否则选表头含 `型号`+`类别` 的第一张；多张都符合时停止并请工程师确认，不擅自合并。

如果结构化字段缺失，允许从 `主要规格` 做**确定性解析**：

- `(\d+)\s*DI`、`(\d+)\s*DO`、`(\d+)\s*AI`、`(\d+)\s*AO`；
- `DC\s*24\s*V`、`24\s*V\s*DC`、`AC\s*220\s*V`、`220\s*V\s*AC`；
- `(\d+(?:\.\d+)?)\s*A`、`(\d+(?:\.\d+)?)\s*mA`；
- `PL\s*[a-e]`、`SIL\s*[1-3]`、`Cat\.?\s*[1-4]`；
- `(\d+)\s*[-~]\s*(\d+)\s*天`、`(\d+)\s*周`。

解析规则：

- 能唯一解析才采用；解析结果和原始字符串写入报告。
- 解析不出、或存在多个互相冲突的值，标 `无法判定`，不参与硬过滤，并列入数据缺口。
- 不得用品牌/型号“猜”参数。
- `替代型号` 列只作参考，**不得直接写进 BOM**；只有该型号在库内有独立行时才能被选。
- 库里的 `数量`/`小计` 是报价口径，不是本项目数量；本项目数量按 IO/回路重新计算。
- 型号匹配时归一化空格/换行，但 BOM 写库内原值；不得改写型号。
- 单价解析去掉货币符号/千分位；无法解析写 `待询价`，不得估一个数。
- 交期解析统一为天；`现货 3-5 天` 取5天，`3周` 取21天；`待定` 视为未知。

## 2. 执行流程

### 2.1 总流程

```text
读输入/验字段
  → 建需求基线（已确认/待定/关闭）
  → 生成 scheme.md（4部分）
  → 从方案抽取信号，生成 IO 草案（已用点）
  → 解析器件库，确定性选型（CPU/模块/电源/继电器/安全件/驱动/执行器）
  → 回填 IO 备用点/预估地址，形成最终 io_list.xlsx
  → 生成 bom.xlsx（库内型号+回路/IO外键）
  → 写校验脚本，执行6项检查，输出 JSON
  → 生成 multi_check_report.md
  → 交付前自检 + 对话摘要（待工程师审阅）
```

### 2.2 两遍 IO（重要）

步骤2-2 在步骤2-3 之前，但**备用点数量/预估地址依赖选型后的硬件总通道**。因此 IO 表按两遍做：

- **第一遍**：从方案抽取“使用中”的物理 IO 和内部/HMI 标签，分配 IO-ID，形成草案；暂不伪造备用点。
- **选型后第二遍**：按已选 CPU/模块总通道，回填显式备用点、预估地址，再做自检。
- 最终交付的是第二遍的 `io_list.xlsx`；第一遍草案可以临时保存，但不得把“未选型前的估计”写成最终硬件容量。

### 2.3 需求基线

对每条 REQ 建索引：`REQ-ID / 内容 / 验收准则 / 优先级 / 状态`。状态归一化：

| 原状态 | 本阶段处理 |
|---|---|
| `已确认` | 可作为方案骨架，可生成正式 IO/BOM |
| `待定` / `待澄清` / `TBD` / `待确认` | 不固化参数；方案做预留；不生成依赖该参数的正式 IO/BOM |
| `【模拟回答】` | 视为未确认；只做预留/报告，不得当客户已确认 |
| `已关闭` | 从方案范围排除；在覆盖表标“不适用/已关闭” |
| 空白/未知 | 视为未确认；报告数据缺口，不擅自当已确认 |

补充：即使 REQ 状态是 `已确认`，只要正文/验收准则里含 `待定/TBD/待确认/待客户确认`，对应参数也按“待定”处理，不得固化；报告列未决项。

规则：

- 没有至少一条 `已确认` REQ 时：
  - `auto_simulate_customer=false`：停止，不生成方案。
  - `auto_simulate_customer=true`：允许以 `【模拟回答】` 条目作为**模拟基线**继续，但必须同时满足：
    1. `scheme.md` 文档头、报告 §0、以及每条相关 REQ 的覆盖行都写 `模拟基线-未获客户确认`；
    2. 相关 REQ 的覆盖状态只能写 `部分覆盖`，不得写 `已覆盖`；
    3. `completion_caveats` 记入“需求基线为模拟基线”。
- 方案中的每个功能段、动作、联锁、控制方式、参数，都必须引用 REQ-ID；没有来源的元素不得保留。
- 客户原话/验收准则里的数值和单位原样使用；不换算、不圆整、不“优化”。
- 两条 REQ 在对象/条件/参数上冲突时，停止该处设计，报告冲突与待裁决选项，不选边。
- 已关闭 REQ 不生成 IO/BOM；若仍被其他 REQ 引用，报告冲突。

### 2.4 方案建议与需求缺口

方案允许提出工程实现建议（顺序、联锁、控制方式），但必须：

- 引用支撑它的 REQ-ID；
- 在备注中标记 `建议/待确认`（如果 REQ 没明确要求该细节）；
- 不得把建议写成新的客户需求；
- 如果完成方案必须新增一条 REQ 才能成立，停止并报告“需求缺口”，不要自行补一条。

### 2.5 交付前总原则

- 先方案，后 IO，再选型，再 BOM，最后自检；不要先选型再倒推方案。
- 选型只从库内；没有合格候选就报告，不编型号。
- 自检只读，不修改三个交付文件。
- 最终状态是“待工程师审阅”，不是“已批准”。

## 3. 需求覆盖与追溯

### 3.1 追溯链

```text
REQ-ID → SEG/STEP/IL/PAR（方案）
       → IO-ID（信号）
       → BOM-ID（器件）
       → CIR-ID（回路）
```

要求：

- 每条已确认 REQ 至少映射到一个方案元素；否则报告“未覆盖”。
- 每个方案元素至少引用一个 REQ；否则删除或报告“无源元素”。
- 每条使用中的物理 IO 至少引用一个 REQ；备用点可引用 `SYSTEM`。
- 每个 BOM 项至少引用一个回路和一个 IO-ID（系统级用 `SYSTEM`）。
- 每项都能反查：从 BOM 能回到 IO，从 IO 能回到 REQ。

### 3.2 需求覆盖状态

| 状态 | 含义 |
|---|---|
| `已覆盖` | 方案、IO、BOM（如适用）均能追溯 |
| `部分覆盖` | 方案已覆盖，但 IO/BOM 因待定/缺件未落 |
| `未覆盖` | 找不到方案落点，必须列整改 |
| `不适用` | 已关闭/非控制类需求，写明理由 |

每个 `未覆盖` 都是高严重度发现；不得用“其他/常规”掩盖。

### 3.3 假设记录

如果必须做工程假设（例如控制方式建议、设备分组），在报告中建 `ASM-xxx`：

```text
ASM-001 | 假设内容 | 依据（REQ/工艺） | 影响 | 待谁确认
```

假设不能用于填写缺失的工艺参数、量程、阈值、精度、安全等级；这些只能“待定/预留”。

## 4. scheme.md 规范

### 4.1 固定结构（4部分）

`scheme.md` 正文必须且只需包含以下4个主部分（可有子节）；文档信息头不计入4部分：

1. **工艺分段划分**
2. **每段动作顺序、联锁条件**
3. **控制方式选型（硬线 / PLC / 变频 / 伺服）**
4. **关键参数与工程预留**

文档头写：项目/版本/日期/输入文件/编制人/状态（`待审阅`）/编制边界。

### 4.2 第1部分：工艺分段划分

表：

| SEG-ID | 功能段 | 范围/边界 | 主要对象/设备 | 关联REQ-ID | 备注 |
|---|---|---|---|---|---|
| SEG-01 | <上料段/检测计数段/分拣段/安全报警段…> | <起点—终点> | <对象> | REQ-… | <建议/待确认> |

要求：

- 分段按工艺流程，不按电气柜/程序块分。
- 每段边界清楚：从什么状态开始、到什么状态结束、与上下游如何交接。
- 每段至少一个 REQ；无 REQ 的段不写。
- 功能段名称可用“上料段、检测计数段、分拣段、安全报警段”等，但必须来自实际工艺。

### 4.3 第2部分：动作顺序与联锁

每段一张动作表：

| STEP-ID | 动作 | 触发条件 | 完成条件/反馈 | 联锁条件 | 故障/安全状态 | 关联REQ-ID |
|---|---|---|---|---|---|---|
| SEG01-ST01 | <对象动作> | <信号/条件> | <到位/计数/时间> | <禁止/允许条件> | <停止/保持/报警/复位> | REQ-… |

联锁汇总表：

| IL-ID | 联锁条件 | 允许动作 | 禁止动作 | 解除条件 | 关联REQ-ID |
|---|---|---|---|---|---|
| IL-01 | <条件> | <动作> | <动作> | <条件> | REQ-… |

要求：

- 动作顺序必须能对应到方案段；不得出现“黑箱自动”。
- 触发/完成/联锁/故障状态四件事写清楚；缺失的写 `待定`，不要编。
- 安全相关动作必须标明是硬线/安全回路还是普通 PLC 逻辑；不能把安全功能只写成软件条件。
- 联锁条件必须可观察（信号/状态），不能写“确保安全”这种不可判定表述。
- 每个 STEP/IL 至少一个 REQ。

### 4.4 第3部分：控制方式选型

表：

| 对象/段 | 控制方式 | 选型理由 | 关键信号 | 关联REQ-ID | 库内候选类别 | 备注 |
|---|---|---|---|---|---|---|
| SEG-01/输送电机 | PLC / 变频 / 伺服 / 硬线 | <为什么> | <DI/DO/AI/AO/内部> | REQ-… | <控制器/变频器/伺服/安全器件…> | <建议/待确认> |

规则：

- `控制方式` 必须明确落到四类之一：`硬线`、`PLC`、`变频`、`伺服`；可加限定语（如“PLC+中间继电器”），但不能含糊写“自动控制”。
- 安全/急停/安全门：优先硬线或安全继电器/安全模块，不得仅靠普通 PLC 软件；若 REQ 明确要求其他架构，报告冲突，待工程师裁决。
- 简单开关量顺序/计数/报警：PLC。
- 需要连续调速的电机：变频。
- 需要位置/转矩闭环的轴：伺服。
- 选择理由必须引用工艺要求/REQ，不得写“常规做法”。
- 这里只选控制方式，不选具体型号；具体型号在器件库选型阶段完成。

回路清单（供 BOM 外键）：

| CIR-ID | 回路用途 | 电压等级 | 关联SEG/REQ | 备注 |
|---|---|---|---|---|
| CIR-SEG-01 | <上料控制> | <24V DC/220V AC> | SEG-01 / REQ-… | <…> |
| CIR-SAFE-ESTOP | <急停安全回路> | <24V DC> | REQ-… | <…> |
| CIR-PWR-24V | <24V控制电源> | <24V DC> | REQ-… | <…> |
| CIR-SYS | <系统级> | <—> | SYSTEM | <CPU/模块等> |

> 安全回路 ID 必须以 `CIR-SAFE-` 开头；普通回路不得使用该前缀。BOM 中的安全器件必须关联 `CIR-SAFE-*`，便于脚本识别；安全功能仍须有 REQ 来源。

### 4.5 第4部分：关键参数与工程预留

参数表：

| PAR-ID | 参数 | 值 | 单位 | 来源REQ | 状态 | 备注 |
|---|---|---|---|---|---|---|
| PAR-01 | <节拍/速度/位置/温度/压力/精度/PL/预算/交期…> | <值或待定> | <单位> | REQ-… | 已确认/待定 | <预留/依据> |

要求：

- 只列需求中出现的参数；不得自造工艺参数。
- 数值必须带单位；无数值写 `待定`，状态写 `待定`。
- `待定` 参数做预留设计：

| 参数 | 待定原因 | 预留方式 | 影响IO/BOM | 需确认人 |
|---|---|---|---|---|
| <参数> | <缺客户值/缺量程/缺安全等级…> | <预留AI通道/预留端子/预留扩展槽/预留软件设定…> | <IO-…/BOM-…/无> | <客户/工艺/安全/电气> |

- 工程预留只写有依据的：DI/DO 15%备用、24V电源≤60%负载率、必要的扩展槽/端子。没有依据的预留不要编数字。
- 预留不等于已确认；报告中必须列入未决项。

需求覆盖表：

| REQ-ID | 优先级 | 状态 | 方案落点（SEG/STEP/IL/PAR） | IO-ID | BOM-ID | 覆盖状态 | 备注 |
|---|---|---|---|---|---|---|---|
| REQ-… | 高/中/低 | 已确认 | SEG-01/STEP-02 | IO-… | BOM-… | 已覆盖 | <…> |

> 不适用的 IO/BOM 写 `—`，不要留空。

### 4.6 方案禁止内容

- 不写 PLC 程序、SCL/LAD/ST/FBD 代码；
- 不写 HMI 画面脚本、控件布局；
- 不写接线图、端子排、CAD、电缆走向；
- 不写具体器件型号（型号放 BOM）；
- 不写未确认的新功能需求。

## 5. io_list.xlsx 规范

### 5.1 固定字段（9列，顺序固定）

```text
IO-ID | 信号名 | 类型 | 预估地址 | 设备标签 | 电压电流规格 | 端子预留字段 | 备用标志 | 关联REQ-ID
```

- 只允许这9列，不加“说明/备注”列；需要解释的内容放 scheme 或 self-check 报告。
- **极性落位（附录 Z.3）**：开关量在 `电压电流规格` 列用固定后缀标注，如 `24VDC/NC`、`24VDC/NO`；模拟量写 `4-20mA` 等即可。阶段3 据此填 `NC语义` 列，阶段4 据此取反。
- **前置类落位（附录 Z.4）**：模式选择、权限登录、参数配置、初始化/复位类点位，在 `信号名` 前加固定前缀 `[PRE]`，如 `[PRE]自动模式选择`。前缀会原样继承到阶段3，禁止在下游删改。
- 第1行是表头；第2行起是数据；无标题行、无合并单元格。
- 新建时工作表名 `IO点表`；只放一张表。
- `IO-ID` 用文本格式保留前导零；其余字段按文本写入（规格/标签/REQ），不要自动转数值。

### 5.2 类型

| 类型 | 含义 | 是否占硬件通道 |
|---|---|---|
| `DI` | 物理数字量输入 | 是 |
| `DO` | 物理数字量输出 | 是 |
| `AI` | 物理模拟量输入 | 是 |
| `AO` | 物理模拟量输出 | 是 |
| `内部` | PLC内部状态/模式/报警/计数/配方等，需要与HMI/程序共享 | 否 |
| `HMI` | HMI画面读写标签、显示/操作标签 | 否 |

`内部` 与 `HMI` 必须分开；不要把 HMI 标签写成 `内部`，也不要把物理点写成“内部”。

### 5.3 IO-ID与预估地址

- `IO-ID` 全表唯一，格式 `IO-001`、`IO-002`…，跨类型统一编号，文本格式保留前导零。
- 首次生成按“DI→DO→AI→AO→内部→HMI”顺序编号；同一类型内按方案出现顺序。
- 同一项目重复运行时，优先按 `设备标签+信号名` 复用已有 IO-ID；新信号取当前最大号+1；已删除的 ID 不复用。若无法安全复用，重建并在报告中说明版本差异。
- `预估地址` 采用**逻辑预估地址**，不代表最终 PLC 物理地址：
  - DI：`DI-001`、`DI-002`…
  - DO：`DO-001`、`DO-002`…
  - AI：`AI-001`…
  - AO：`AO-001`…
  - 内部/HMI：`—`
- 最终 PLC 地址在硬件组态阶段确定；本表默认不分配真实 I/Q 地址，避免跨品牌误套。若项目明确要求 PLC 地址格式，可按选定 CPU 的地址体系回填，并标“预估，最终以硬件组态为准”。

### 5.4 信号抽取

从方案逐条抽取，至少覆盖：

- 每个动作的**命令输出**（DO/AO）；
- 每个动作的**反馈/到位/检测**（DI/AI）；
- 每个联锁的**条件信号**（DI/AI/内部）；
- 每个模式的**状态/切换**（内部/HMI）；
- 每个报警的**触发/复位/显示**（内部/HMI，必要时DO）；
- 每个模拟量控制的**设定/反馈**（AI/AO/HMI）；
- HMI 操作/显示标签（HMI）；
- 明确预留的备用点（DI/DO/AI/AO，`备用`）。

规则：

- **一个物理信号一条记录**；不得把多个物理点合并成一条。
- 同一物理器件的多个信号（如编码器A/B/Z）可以多条 IO，但 BOM 只算一个器件；`关联IO-ID` 在 BOM 侧列出全部。
- 同一信号被多条 REQ 使用，只建一条 IO，`关联REQ-ID` 列出多条，不重复建点。
- 同一 `设备标签` 不得对应两个不同物理信号；同一信号不得出现两条 IO。
- 内部/HMI 标签只收录需要跨程序/HMI共享的持久标签；临时变量不入表。

### 5.5 信号名与设备标签

推荐命名（不是强制，但必须唯一）：

- `信号名`：中文可读，如 `上料段-输送电机-运行命令`。
- `设备标签`：唯一 ASCII 标签，如 `SEG01_M1_RUN`；HMI 用 `HMI_AutoMode`，内部用 `INT_SeqStep`。
- 安全侧常闭：`信号名` 必须含 `NC/常闭/安全侧`，如 `急停按钮-NC-安全侧`；`设备标签` 如 `ESTOP_NC`。
- 若需求明确要求 NO，按 NO 记录，并在报告中标“安全侧NO，待安全工程师确认”；不得擅自改成 NC。
- 模拟量：`信号名` 可含测点，`电压电流规格` 必须含量程和信号类型。

### 5.6 电压电流规格

必须写清“电压 / 电流或信号 / 量程（模拟量）”，例如：

| 类型 | 建议写法 |
|---|---|
| DI 干接点 | `24V DC / 干接点` |
| DI 传感器 | `24V DC / <mA>`；未知写 `24V DC / 待定` 并报告 |
| DO 继电器线圈 | `24V DC / <A>` 或 `24V DC / 继电器线圈` |
| DO 电磁阀 | `24V DC / <A>（经中间继电器）` |
| AI | `4-20mA / 24V DC / 量程 <下限>~<上限> <单位>` 或 `0-10V / 量程 …` |
| AO | `4-20mA / 0-10V / 量程 …` |
| 内部/HMI | `—` |

- 模拟量必须写量程和信号类型（4-20mA 或 0-10V）；缺一不可落表，应报告缺口。
- 物理输出驱动感性负载时，`电压电流规格` 写负载额定值，并在 BOM 中配中间继电器；不要用 IO 表替代继电器选型。
- 24V 负载计算的电流以 BOM/器件库额定值为准；IO 表的规格用于信号匹配，不重复计入。

### 5.7 端子预留字段

只表示预留提示，不做端子排/接线设计：

| 类型 | 建议值 |
|---|---|
| DI/DO | `预留2位` |
| AI/AO | `预留3位`（信号+/信号-/屏蔽） |
| 内部/HMI | `—` |
| 备用 | `预留2位` |

### 5.8 备用标志

只允许：

- `使用`：使用中的物理点或内部/HMI标签；
- `备用`：显式列出的备用物理通道；
- `—`：内部/HMI标签（不占硬件通道）。

规则：

- 备用点必须逐点一行，`信号名` 写 `备用-DI-01` 等，`设备标签` 写 `SPARE_DI_01` 等，禁止写“其他/若干”。
- 备用点 `关联REQ-ID` 可写 `SYSTEM`，或写预留所属段的 REQ；报告中说明。
- 备用行不得被 BOM 当作现场设备关联；备用点不选器件。
- 显式备用行数不得超过硬件实际未占用通道数；至少列出满足15%备用比例所需的备用点（DI/DO）。

### 5.9 关联REQ-ID

- 必填；多条用 `;` 分隔。
- 必须是需求表中存在的 REQ-ID；备用点可用 `SYSTEM`。
- `SYSTEM` 只用于备用/系统级，不得用于有明确需求来源的现场信号。
- 内部/HMI 标签也必须有 REQ 来源，不能凭空建。

### 5.10 排序与校验

排序：`DI→DO→AI→AO→内部→HMI`，同类型按 IO-ID 升序。

落表前校验：

- 9列表头逐字正确；
- IO-ID 唯一、格式正确；
- 物理点/内部/HMI 分类正确；
- 模拟量有量程+信号类型；
- 安全侧常闭有 NC/安全侧标识；
- 备用点逐点列出；
- 内部/HMI 的预估地址/端子/备用标志为 `—`；
- 关联REQ-ID 存在（或 `SYSTEM`）；
- 无重复物理信号。

## 6. 器件库解析与确定性选型

### 6.1 选型输入摘要

从 `io_list.xlsx` + `scheme.md` + 需求表汇总：

| 摘要项 | 来源 | 用途 |
|---|---|---|
| 物理IO数量（DI/DO/AI/AO，使用中） | IO表 | CPU/模块容量 |
| 备用目标（DI/DO≥15%） | IO表/方案 | 容量目标 |
| 电压等级 | IO表规格、方案回路 | 器件电压匹配 |
| 负载类型/电流 | IO表、方案、需求 | 继电器/输出/电源 |
| 安全功能与PL | 需求、方案安全段 | 安全器件过滤 |
| 预算 | 需求表/用户指令 | 成本检查 |
| 交期上限 | 需求表/用户指令 | 关键器件交期 |
| 现有设备 | 需求/用户说明 | 不重复采购，报告列明 |

如果某个摘要项无法确定：

- 不阻塞方案/IO草案；
- 但对应选型/检查标 `无法判定`；
- 在报告中列“需补充数据”，不得猜。

#### 6.1.1 类别归一

器件库类别名可能不同；选型和自检前先做归一映射，映射结果写入报告。无法归一的类别不得硬套，标“类别未识别”。

| 规范类别 | 库内常见别名 | 用于 |
|---|---|---|
| `CPU/控制器` | `CPU`、`PLC`、`控制器`、`可编程控制器` | 容量/预算/交期/追溯 |
| `DI模块` | `数字量输入模块`、`DI模块`、`输入模块` | 容量 |
| `DO模块` | `数字量输出模块`、`DO模块`、`输出模块` | 容量/感性负载 |
| `AI模块` | `模拟量输入模块`、`AI模块` | 容量 |
| `AO模块` | `模拟量输出模块`、`AO模块` | 容量 |
| `混合IO模块` | `I/O模块`、`混合模块`、`扩展模块` | 容量（按实际类型拆分） |
| `电源` | `开关电源`、`24V电源`、`电源模块` | 24V负载率 |
| `中间继电器` | `继电器`、`继电器模块`、`接口继电器` | 感性负载隔离 |
| `安全器件` | `安全继电器`、`安全模块`、`急停按钮`、`安全门开关`、`安全接触器` | PL检查 |
| `变频器` | `变频器`、`VFD` | 控制方式/交期 |
| `伺服` | `伺服驱动器`、`伺服电机`、`伺服` | 控制方式/交期 |
| `HMI` | `HMI`、`触摸屏`、`人机界面` | BOM/交期 |
| `传感器` | `传感器`、`接近开关`、`光电开关`、`编码器` | BOM/IO |
| `执行器` | `电磁阀`、`接触器`、`指示灯`、`蜂鸣器`、`电机` | BOM/IO/负载 |

> CPU/扩展模块如果只有“总IO数”而没有 DI/DO/AI/AO 分类型通道数，不能用于 S2-01/S2-02 的分类型核算；标 `无法判定`，不得按比例拆分猜测。

### 6.2 候选器件集合

对每个选型对象（CPU、模块、电源、继电器、安全件、驱动、执行器、传感器等）：

1. 按 `类别` 从器件库取候选；
2. 逐项做硬过滤；
3. 记录每个候选的通过/淘汰原因；
4. 通过全部硬过滤的即“候选集”；
5. 从候选集按确定性排序取第一项；
6. 候选集与淘汰原因写入 `multi_check_report.md` 的“选型过滤记录”。

候选集是报告内容，不新增输出文件；BOM 只放最终选中项。

### 6.3 硬过滤维度

| 维度 | 判定 | 数据来源 | 不通过处理 |
|---|---|---|---|
| 类别 | 与对象所需类别一致 | 器件库 `类别` | 淘汰 |
| IO数量 | CPU/模块的 DI/DO/AI/AO ≥ 该对象需求（含备用目标） | 器件库通道数/主要规格 | 淘汰 |
| 电压 | 与回路电压/信号类型兼容 | 器件库 `电压`/主要规格 | 淘汰 |
| 电流 | 额定电流/触点容量 ≥ 计算负载电流 | 器件库 `电流`/主要规格 | 淘汰 |
| 安全等级 | 安全器件 PL ≥ 该安全功能要求 PL | 器件库 `安全等级`、需求 | 淘汰 |
| 预算 | 有单件上限时 ≤上限；总预算在汇总后校验 | 需求/用户、器件库单价 | 超限淘汰或汇总报警 |
| 交期 | 有交期上限时 ≤上限；关键器件必查 | 需求/用户、器件库交期 | 超限淘汰 |
| 数据完整性 | 必需字段齐全、可解析 | 器件库 | 标“数据不足”淘汰 |

补充：

- 电压必须区分 DC/AC 和等级；24V DC 线圈不能直接由 220V AC 输出驱动。
- 电流比较用同一口径（A 或 mA）；区间/范围取上限做保守判断。
- 安全等级按 PL 排序：`PL a < PL b < PL c < PL d < PL e`。
- 如果库用 `SIL`/`Cat.` 而需求是 PL，不得直接换算；标“等级体系不一致”，交工程师确认。
- 预算：若只给总预算，不把总预算硬摊到单件；先选技术合格的最低成本方案，汇总后检查。若给单件上限，则按上限硬过滤。
- 交期：单位统一为天；周×7，区间取上限；`待定` 视为无法判定。

### 6.4 确定性排序

通过全部硬过滤后，按以下顺序取第一项：

| 对象 | 排序 |
|---|---|
| 非关键器件 | 单价升序 → 交期升序 → DEV-ID 升序 |
| 关键器件（CPU、安全件、变频/伺服、电源、HMI等） | 交期升序 → 单价升序 → DEV-ID 升序 |

- 不允许随机、不允许按“感觉/品牌偏好”排序。
- 关键器件可在器件库用 `关键器件=是` 标记；没有标记时按类别默认。
- 同价同交期时按 DEV-ID 字典序，保证可复现。
- 选中理由写入报告；未选候选的淘汰原因也要写。

### 6.5 CPU与扩展模块

1. 计算各类型目标容量：
   - DI：`ceil(used_DI / 0.85)`；
   - DO：`ceil(used_DO / 0.85)`；
   - AI/AO：至少 `used_AI`/`used_AO`（可留工程余量，但不得编造）。
2. CPU 候选按 6.4 的关键器件排序（交期→单价→DEV-ID）逐一试算；若工程师明确指定价格优先，记录指令来源后再调整。
3. 对每个 CPU，计算各类型缺口 = 目标容量 − CPU集成通道。
4. 缺口 >0 时，从库内同类型模块中按 `单价/通道数` 升序、交期升序、DEV-ID 升序选模块，直到补齐；混合模块只按实际可用类型计入。
5. 计算 CPU+模块总价与最大交期；取第一个满足容量/电压/安全/交期/预算的组合。
6. 若所有组合都超预算，选总价最低的合规组合，报告“超预算”，不自动降级技术规格。
7. 若没有任何组合满足容量，停止该部分，报告“无库内合格CPU/模块组合”。

报告必须列出：试算的CPU、模块组合、总通道、总价、交期、淘汰原因。

### 6.6 电源、继电器、安全件

- **24V电源**：按 BOM 中24V控制母线负载电流 / 0.60 计算所需容量；从库内选 24V DC 电源，输出电流≥所需，按单价/电流、交期、DEV-ID 排序；数量按所需/单台容量向上取整。
- **中间继电器**：每个感性负载 DO 必须有中间继电器隔离；按线圈电压、触点容量、通道数过滤；数量=ceil(感性DO数/模块通道数)；`关联IO-ID` 列出覆盖的 DO。
  - 如果使用继电器输出型 DO 模块替代中间继电器，报告中标“等效隔离待工程师确认”，不得直接判通过。
- **安全器件**：急停按钮、安全继电器/模块、安全门开关、安全回路接触器等，PL 必须≥该安全功能要求；缺 PL 数据标“无法判定”，不得用普通器件替代。
- **变频/伺服**：按电机功率/电压/控制方式/反馈类型过滤；库内无合格项就报告，不编型号。
- **传感器/执行器**：按信号类型、量程、电压、负载、环境要求过滤；量程/精度未知时不得猜，标待定。

### 6.7 禁止事项

- 禁止写库外型号、替代型号、品牌+猜测型号。
- 禁止把“同等性能”“可替代”写成 BOM 型号。
- 禁止用价格估算/市场价替代库内单价。
- 禁止为了凑预算选不满足 PL/电压/电流的器件。
- 禁止在方案里写具体型号（型号只出现在 BOM/选型记录）。

## 7. bom.xlsx 规范

### 7.1 固定字段（10列，顺序固定）

```text
BOM-ID | 类别 | 名称 | 型号 | 数量 | 单价 | 小计 | 供应商 | 关联回路 | 关联IO-ID
```

- 只允许这10列；不加“选型理由/备注/DEV-ID”列。选型理由放报告。
- 第1行表头；第2行起数据；无标题行、无合并单元格。
- 新建时工作表名 `BOM清单`；只放一张表。
- `BOM-ID` 用文本格式；`数量`整数；`单价/小计`数值（2位小数）或`待询价`文本。

### 7.2 取值规则

| 字段 | 规则 |
|---|---|
| `BOM-ID` | `BOM-001`…，表内唯一，文本格式 |
| `类别` | 取器件库 `类别`；不得自造类别 |
| `名称` | 取器件库 `名称` |
| `型号` | 取器件库 `型号`，逐字一致；必须能在库中回查 |
| `数量` | 正整数；按物理器件数/回路计算，不按 IO 行数 |
| `单价` | 取器件库单价；无价格写 `待询价`；区间价取上限，并在报告中注明 |
| `小计` | 数量×单价，2位小数；单价`待询价`时写`待询价`，不得写0 |
| `供应商` | 取器件库供应商；仅有品牌时写品牌，并在报告中注明“品牌代供应商，待采购确认”；缺失写`待确认` |
| `关联回路` | 一个或多个 `CIR-…`，`;`分隔；不得空白 |
| `关联IO-ID` | 一个或多个 `IO-…`，`;`分隔；系统级写 `SYSTEM`；不得空白 |

### 7.3 数量计算

- CPU：1（无冗余要求时不加）。
- 扩展模块：按选型组合数量。
- 电源：按负载/0.60容量向上取整。
- 中间继电器：按感性DO/模块通道数向上取整。
- 传感器/执行器：按物理器件数，不按信号数；同一器件多信号只算1，`关联IO-ID`列全。
- 安全继电器/接触器：按安全回路/功能数量；不得凭感觉加。
- 变频器/伺服：按轴/电机数量。
- HMI：按需求数量；无需求不选。
- 现有设备：不进 BOM；在报告中列“现有设备/不采购”，并保留 IO 追溯。
- 电缆、端子、线槽、柜体等施工材料默认不进本阶段 BOM；只有需求明确、器件库有对应项时才纳入，并在报告中注明。不得在本阶段做接线/长度设计。

### 7.4 分组与外键

- 同一型号+供应商+同一回路/用途可合并为一行，数量为器件数；`关联IO-ID`列出该行覆盖的全部信号。
- 不同回路/不同用途分开，避免一个 BOM 行跨太多回路导致追溯不清。
- CPU/模块等系统级器件用 `关联回路=CIR-SYS`、`关联IO-ID=SYSTEM`；电源用 `CIR-PWR-24V`；安全器件用 `CIR-SAFE-*`；现场器件用 `CIR-SEG-*`。
- 现场器件必须关联实际 IO，不得用 `SYSTEM` 偷懒。
- 每个 `关联回路` 必须在 scheme 的回路清单中存在；每个 `关联IO-ID` 必须在 io_list 中存在（或 `SYSTEM`）。
- 每个使用中的物理 IO 应有至少一个 BOM 器件，或在报告中列“现有设备/不采购/预留”；否则追溯缺口。

### 7.5 金额与预算

- 金额保留2位小数，四舍五入；脚本用 `Decimal`，不用二进制浮点累加。
- BOM 合计 = 所有数字小计之和；`待询价` 不计为0，单独统计项数。
- 预算检查使用“已计价合计+待询价项数”；有待询价项时不能判预算通过。
- 单价口径为器件库单价，不含税费/运费/安装，除非库字段明确包含；报告写明。
- 区间价取上限；不取中值、不自行议价。

### 7.6 库内校验

生成 BOM 前/后必须校验：

- 每个 `型号+供应商` 能在器件库找到；若库内供应商缺失、BOM 写 `待确认`，则只按型号匹配并报告供应商缺口，不视为库外型号；
- 型号不是库外“替代型号”；
- 单价与库内一致（或明确标待询价）；
- 小计=数量×单价；
- 关联回路/IO存在；
- BOM-ID 唯一。

任何库外型号：**停止生成 BOM**，报告具体行和型号；不得静默删除或改成“近似型号”。

## 8. 六项自检

### 8.1 总则

- 六项检查必须由脚本执行，结果落盘 JSON；报告中的数字从 JSON 读取，不允许 LLM 估算或手写。
- 脚本只读 `requirements_spec.xlsx`、`device_library.xlsx`、`io_list.xlsx`、`bom.xlsx`，不得修改它们；预算/交期/PL 若不在需求表，可通过命令行参数传入，并在报告中注明来源。
- 每项结果只能是：`通过`、`不通过`、`无法判定`、`不适用`。
- 不通过/无法判定必须给具体证据与整改建议；不自动修改。
- 六项之外，另做“数据一致性/追溯性”校验，单独列出，不替代六项。

### 8.2 S2-01 IO容量

**目的**：确认物理 IO 不超过 CPU+扩展模块总通道，且 DI/DO 占用≤85%。

数据：

- `used_DI/DO/AI/AO` = io_list 中 `类型` 对应且 `备用标志=使用` 的物理行数；
- `total_DI/DO/AI/AO` = BOM 中 CPU+扩展模块按类型通道数×数量之和；
- 内部/HMI、备用行不计入 `used`。

判定：

1. 每种类型 `used ≤ total`；否则不通过。
2. DI/DO 分别计算 `occupancy = used/total`；`total>0` 时要求 `occupancy ≤ 85%`；否则不通过。
3. `total=0` 且 `used=0`：该类型不适用；`total=0` 且 `used>0`：不通过。
4. 合计值 `(used_DI+used_DO)/(total_DI+total_DO)` 作为证据输出，不替代分类型判定。

证据：分类型 `used/total/occupancy/spare`；选中的 CPU/模块清单。

整改建议：增加扩展模块、减少/合并IO、调整方案；不得改备用行来“凑”通过。

### 8.3 S2-02 备用通道比例

**目的**：DI/DO 未占用通道≥15%。

判定：

1. `spare_ratio = (total - used)/total`，DI/DO 分别计算；
2. `total>0` 时要求 `spare_ratio ≥ 15%`；否则不通过；
3. 合计备用率作为证据；
4. 显式备用行数 `spare_rows` 不得超过 `total-used`；超过则不通过（备用点造假）；
5. 显式备用行数少于满足15%所需的点数时，报告“备用点未逐点列足”的数据缺口；建议至少列出 `ceil(15%×total)` 个。

注意：备用率按硬件总通道−使用通道计算，不按显式备用行数计算；显式备用行是文档证据，不是分母。

整改建议：增加通道/模块、减少占用、补列备用点；不得把使用点改成备用。

### 8.4 S2-03 输出类型匹配（感性负载）

**目的**：电磁阀等感性 DO 必须配置中间继电器隔离。

数据：

- 感性 DO 识别：IO表 `信号名/设备标签` 含 `电磁阀/YV/阀/接触器线圈/制动器/感性/solenoid/valve`，或 BOM/器件库 `负载类型=感性`；
- BOM 中间继电器：`类别` 含 `中间继电器`/`继电器模块`，`关联IO-ID` 覆盖该 DO；
- 继电器线圈电压、触点容量、通道数从库内读取；缺失时标 `无法判定`，不得猜；
- 继电器线圈电压与 DO 电压兼容，触点容量≥负载电流。

判定：

1. 无感性 DO：不适用；
2. 每个感性 DO 必须至少被一个中间继电器 BOM 行覆盖；否则不通过，列出缺失 DO；
3. 继电器数量×通道数 ≥ 覆盖的 DO 数；否则不通过；
4. 线圈电压/触点容量不匹配：不通过；
5. 负载类型无法判定：无法判定，要求补充；
6. 用继电器输出型 DO 模块替代中间继电器：标 `无法判定`，报告“等效隔离待确认”，不得直接通过。
7. 其他感性负载（接触器线圈、制动器等）按同一原则检查；若需求只点名电磁阀，至少覆盖电磁阀，其他感性负载列为建议核查。

整改建议：从库内选中间继电器、核对线圈/触点、补 BOM 关联；不得用普通 DO 直接驱动电磁阀。

### 8.5 S2-04 24V控制电源负载率

**目的**：24V 控制电源负载率≤60%。

数据：

- 24V 负载电流：BOM 中接入24V控制母线的器件，按 `数量×额定电流` 求和；只有功率时 `I=P/24V`；传感器/继电器/模块/CPU/HMI等按库内额定值；
- 24V 电源容量：BOM 中为24V控制母线供电的电源，按额定输出电流×数量求和；
- 排除 AC 负载、独立供电负载、非24V器件。
- 电流口径：CPU/模块/HMI取自身消耗电流，不取输出通道额定电流；电源取输出电流（只计供电能力，不计入负载）；继电器取线圈电流；传感器取消耗电流；执行器取负载电流。字段口径不清时无法判定。

判定：

1. 无24V负载：不适用；
2. 无24V电源或容量为0：不通过；
3. 任一带载器件电流缺失/无法解析：无法判定；
4. `load_rate = load_current / supply_current ×100%`；≤60%通过，>60%不通过。

**模拟模式（仅 `auto_simulate_customer=true`）**：第 3 条不再直接判 `无法判定`，改为按保守上限估计并给确定结论：

| 类别 | 保守取值 | 说明 |
|---|---|---|
| CPU/PLC 本体 | 0.7 A | 取偏大常用值 |
| 扩展模块 | 0.2 A/块 | 每块 |
| 传感器（光电/接近/对射） | 0.05 A/只 | 含余量 |
| 继电器/安全继电器 | 0.05 A（线圈） | 每只 |
| HMI 触摸屏 | 1.0 A | 12″ 级 |
| 其它 24V 器件 | 0.05 A/只 | 兜底 |

约束：

- 每一处模拟取值必须标 `【模拟裁决】`，并在报告“待复核”栏逐项列出：器件、缺什么、取了什么、怎么实测；
- 模拟只把“数据缺失 → 无法判定”变成“保守估计 → 通过（模拟）/不通过”，**不得放宽 60% 限值**；估计后超过 60% 仍判 `不通过`；
- 最终 `multi_check_report.md` 的 S2-04 结论不得停留在 `无法判定`；禁止把未知电流按 0 计。

证据：负载清单（BOM-ID/型号/数量/电流）、电源清单、总电流、负载率。

整改建议：增加电源、降低负载、改用低功耗器件、分路供电；不得把未知电流按0计。

### 8.6 S2-05 安全等级

**目的**：急停/安全回路器件满足对应 PL。

数据：

- 安全功能及要求 PL：优先从需求表读取；若只在方案中，作为脚本参数传入并注明来源；脚本不解析自然语言猜测；
- 安全回路器件：BOM 中 `关联回路` 含 `CIR-SAFE-ESTOP`/安全回路，或 `类别` 为急停/安全继电器/安全门/安全接触器；
- 器件 PL：器件库 `安全等级`。

判定：

1. 无安全功能/急停要求：不适用；
2. 有安全要求但未给 PL：无法判定，要求补充；
3. 安全回路器件缺 PL：无法判定；
4. 每个安全器件 PL ≥ 要求 PL：通过；任一不足：不通过；
5. 库用 SIL/Cat. 而需求用 PL：无法判定，要求工程师映射，不得自行换算；
6. 器件不在 BOM（现有/缺失）：无法判定，说明缺哪项。

局限：本检查只核对器件额定 PL，不验证安全架构、类别、诊断覆盖率、接线与验证；这些属于下游安全设计，不得声称“安全功能已认证”。

**模拟模式（仅 `auto_simulate_customer=true`）**：第 2 条（有安全要求但未给 PL）不再判 `无法判定`，改由**模拟安全评估**给出要求等级：

- 默认取 `PL d`（急停、出入口人员防护、超限保护这类人身安全功能不得低于 PL d，也不得低于库内实有安全器件的最高等级）；
- 在报告与 `scheme.md` 中写 `【模拟裁决】要求 PL d（依据：风险等级与库内安全件可达等级；风险：需按 GB 17907 与项目风险评估复核）`；
- 器件 PL 不足时**仍判 `不通过`**，不得因为要求是“模拟出来的”就调低要求；
- 该模拟要求必须进入 `completion_caveats` 与最终报告“待复核”栏。

整改建议：换用库内更高 PL 器件、补齐安全器件、补充 PL 要求；不得降低安全要求来通过。

### 8.7 S2-06 预算、关键器件交期

**目的**：BOM 不超预算；关键器件交期满足要求。

数据：

- 预算：需求/用户明确给出；总预算或单件上限；脚本以参数接收并记录来源；
- BOM 已计价合计、待询价项数；
- 关键器件：`关键器件=是` 或类别为 CPU/安全件/变频/伺服/电源/HMI；
- 交期上限：需求/用户明确给出，统一为天；脚本以参数接收并记录来源。

判定：

1. 未提供预算：无法判定（报告已计价合计，不判通过）；
2. 有待询价项：无法判定（预算不完整）；
3. `已计价合计 > 预算`：不通过，给出差额/比例；
4. 未提供交期上限：无法判定（报告关键器件最大交期）；
5. 关键器件交期缺失：无法判定；
6. 任一关键器件交期 > 上限：不通过；
7. 全部满足：通过。

**模拟模式（仅 `auto_simulate_customer=true`）**：第 1/2/4/5 条的 `无法判定` 改为模拟裁决后给确定结论：

- **预算未提供** → 模拟客户给出预算：取 `已计价合计 × 1.15`（含 15% 余量），标 `【模拟裁决】`；
- **存在待询价项** → 按同类别已计价器件单价的中位数补齐后再算合计，待询价项在 BOM 中**仍保留 `待询价` 原值**，只在报告中给出估算合计并标 `【模拟裁决】`；
- **交期上限未提供** → 取关键器件最大交期的 `+14 天`，标 `【模拟裁决】`；
- 模拟取值后若超预算/超交期，仍判 `不通过`；不得放宽。
- 报告“待复核”栏逐项列出模拟的预算、交期上限与估算单价。

整改建议：调整预算、选库内更低成本合规项、调整交期/替代交期更短的库内项；不得选库外型号或降级安全件。

### 8.8 附加数据一致性校验

这些不是六项必检的替代，但必须先做；任何高严重度问题都要进入报告：

- xlsx 真实、表头逐字、无多余列；
- IO-ID/BOM-ID 唯一、格式正确；
- BOM 型号+供应商在库内；单价与库一致；
- 小计=数量×单价；待询价一致；
- 关联回路存在；关联IO-ID存在或`SYSTEM`；
- 安全器件必须关联 `CIR-SAFE-*`；未关联标追溯缺口/无法判定；
- 每个使用中物理IO有BOM器件或“现有设备/不采购”说明；
- 每个已确认REQ有方案落点；每个方案元素有REQ；
- 安全侧常闭标识、模拟量量程/信号类型、内部/HMI的`—`字段；
- 备用行不超过实际未占用通道；
- 无PLC/HMI代码、接线图、CAD等越界内容。

### 8.9 脚本契约

建议把校验脚本写到临时目录（如 `./.stage2_check/check.py`），不要把脚本当交付物；交付目录只保留四个文件。

脚本输入：四个文件路径（可选预算/交期/PL 参数）。输出：

- `./.stage2_check/check_results.json`（机器可读）；
- `multi_check_report.md` 的“六项结果/发现明细/数据一致性”部分（优先由脚本直接生成完整报告）；
- stdout 摘要（通过/不通过/无法判定数量、退出码）。

退出码：

| 码 | 含义 |
|---|---|
| 0 | 六项全部通过（附加校验无高严重度） |
| 1 | 至少一项不通过 |
| 2 | 无“不通过”，但存在“无法判定” |
| 3 | 输入/表头/字段错误，无法检查 |

JSON 契约见附录 C。报告中的数值必须与 JSON 一致；脚本只读输入文件，不修改它们。

### 8.10 不自修改

六项检查发现任何问题时：

- 不修改 `scheme.md`、`io_list.xlsx`、`bom.xlsx`；
- 不自动加继电器、换CPU、加电源、改预算；
- 只写 `multi_check_report.md` 的发现和整改建议；
- 工程师确认后，才可在新一轮修改并重跑。

> 编号规则在各技能内唯一，交付前逐条打勾；任一条不满足不得声明阶段完成。

### Z.1 BOM 必须覆盖"被控对象本体"（B-01 · 强制）

除电气物料外，BOM 应覆盖被控机械本体（可动机构、电机、执行机构、结构件）；库内有对应项则列入 BOM，库内无对应项时按下列方式登记缺口，不得编造型号：

- 必须在 `multi_check_report.md` 里登记为**结构缺口**（编号 OPEN-xx），不得静默通过
- 不得以"第三方成套/接口预留"一笔带过整类本体

> 真实事故：25 行 BOM 全是电气件，无执行机构、无动力电机、无钢结构 → 数字孪生做出来"没有任何东西可以动作"，装配/孪生/施工三方都无法落地。

### Z.2 反馈点必须有器件行或显式缺口（B-02 · 强制）

每个 DI/AI 反馈点必须能回指一个 BOM 器件；不能时逐点登记缺口，并写明"该点当前由谁承载"。
> 真实事故：13 路热继电器过载反馈无对应 BOM 器件（`OPEN-01/02`），长期悬空。

### Z.3 极性必须逐点写明（B-03 · 强制）

IO 表必须给出每点的**极性语义**（`NC:TRUE=正常` / `NO:TRUE=动作`），供阶段4取反、供阶段5构造激励。落位方式见 §5.1：写在 `电压电流规格` 的固定后缀（`/NC`、`/NO`），**不新增列**（本表固定 9 列）。只写信号名不写极性的，视为缺陷，自检 B-03 判不通过。

### Z.4 标注"前置类"点位（B-04 · 强制）

模式选择、权限登录、参数配置、初始化/复位类点位，必须在 `信号名` 前加 `[PRE]` 前缀作为**前置类**标记（落位见 §5.1，不新增列）；阶段5 构造用例前置态时必须先置这些点。
> 用途：阶段5 构造用例前置态时必须先置这些点，否则流程天然起不来（真实事故：15 条用例因此全部失败）。
